4 adımlı kalıp

Bir parçayı çizerken her seferinde şu dört şeyi söyle:

  1. Ne: "This is a queue."
  2. Neden: "…so accepting work is decoupled from doing it."
  3. Neyi riske atıyor: "Delivery is at-least-once…"
  4. Nasıl kapatıyorum: "…so consumers are idempotent."

Örnek:

I'll put an LLM gateway here. Models are slow, expensive and rate-limited, and one tenant could burn the whole quota. So the gateway enforces per-tenant budgets and falls back to another model if the provider is down.

Başlarken

Before I jump into the design, I'd like to clarify the scope and a few requirements.
Who are the consumers of this API: our own frontend, third-party integrations, or other internal services?
Out of scope for now: billing and the admin UI. I'll mention them at the end if time allows.

API aşaması

Let me start with the resources and the contract, because the contract is the hardest thing to change later.
This operation can take minutes, so instead of holding the request open I'll return 202 with an operation resource the client can poll.

Mimari ve trade-off

This is the simplest version that works. Where would you like me to go deeper?
The trade-off here is eventual consistency: the user sees the change within a few seconds instead of immediately. For content that's acceptable, but not for permissions.
I'd start with Postgres because the team already runs it well; I'd only move to something else when we hit a concrete limit.

Takıldığında

Let me trace one request and find the first place where state changes.

Puan kaybettiren hatalar

  1. Gereksinim sormadan kutu çizmeye başlamak.
  2. API'yi atlayıp direkt mimariye geçmek (turun adı "API Development").
  3. Hata modelini, sayfalamayı, idempotency'yi unutmak.
  4. "Kafka/Cassandra koyalım" deyip neden sorusuna cevap verememek.
  5. Multi-tenancy'yi (tenant izolasyonu) unutmak.
  6. Operasyon tarafını unutmak: deploy, rollback, SLO, alert, on-call.
  7. İlk tasarımı fazla karmaşık yapmak. Önce basit v1, karmaşıklık sorulunca.
  8. Sessiz kalmak ya da ipucuna savunmaya geçmek.

Hafızanı düzelt: 8 yanlış refleks

  1. Kuyruk sıralaması = sahiplik/kilit değil.
  2. JWT doğrulaması = anında iptal değil. Kısa ömürlü token, iptalin token süresi kadar gecikebileceğini kabul etmektir.
  3. İçerik değişmedi = izin değişmedi değil.
  4. 202 = kalıcı kabul. Kaydetmediğin işi kabul etme.
  5. Timeout sonrası dış yan etki belirsiz olabilir.
  6. Mülakat aracında bir özelliğin görünmesi = kullanma izni değil. Sor.
  7. Mutex sadece tek process'i korur; birden çok replika = DB transaction / atomik update.
  8. Streaming = dayanıklı yürütme değil.
