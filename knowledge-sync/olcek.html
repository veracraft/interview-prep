Follow-up soruları

Önce soruyu oku, 20 saniyede kendi cevabını sesli söyle, sonra aç. Genel sorular: Genel takip soruları.

1. A big tenant connects 5 million documents. What happens to the other tenants?

Ana fikir: Tenant başına eşzamanlılık sınırı ve iki şerit: ilk yükleme (backfill) ve canlı değişiklikler ayrı.

Each tenant gets a concurrency limit, so one onboarding can't take all workers. I'd also split backfill from live changes, so small tenants' updates don't wait behind five million documents.
2. The source API returns 429.

Ana fikir: Kaynak başına token bucket, Retry-After'a uy, mesajı gecikmeli tekrar kuyruğa koy; worker'ı uyutma.

We keep a token bucket per tenant and source in Redis, respect Retry-After, and re-queue the work with a delay instead of making the worker sleep, so other sources keep moving.
3. A webhook gets lost.

Ana fikir: Webhook hız içindir, doğruluk polling'den gelir; periyodik polling devam eder.

Webhooks make us faster, polling makes us correct. The periodic sync with the delta cursor still runs, so a lost webhook only delays the change.
4. Someone's access is removed. How fast is it reflected?

Ana fikir: Öncelikli acl-changes şeridi; SLO p99 < 5 dk; arama fail closed.

Permission changes go through a separate priority topic and worker, so they don't wait behind a big sync. The target is under five minutes at p99, and search fails closed if permissions are unknown.
5. The source's cursor token expires.

Ana fikir: Kontrollü tam tarama; hash ile değişmeyenleri atla; upsert sayesinde tekrar zararsız.

Then I do a controlled full rescan for that source. Unchanged documents are skipped by hash, and because writes are upserts, nothing gets duplicated.
6. How do you scale the workers?

Ana fikir: Lag'e göre (KEDA); üst sınır partition sayısı; asıl sınır kaynak kotaları.

Workers scale on consumer lag, not CPU, up to the number of partitions. In practice the source quotas are the real limit, so more workers only help up to that point.
