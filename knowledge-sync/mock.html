Knowledge Sync · Mock mülakat

Gerçekçi, kısaltılmış bir API Development & Solutions Design görüşmesi. Interviewer doğal İngilizce konuşuyor; aday (sen) basit B2 İngilizcesiyle. Amaç sıra, gerekçe ve sakinlik.

Nasıl çalışılır?
  1. Bir kez baştan sona sesli oku; iki rolü de sen oku.
  2. "Adayın cevaplarını gizle"ye bas. Interviewer'ı oku, cevabı kendi cümlelerinle sesli söyle, sonra gizlemeyi kapatıp karşılaştır.
  3. Telefonla kendini kaydet. Cevaplar 20-40 saniyeyi geçiyorsa kısalt.
Yeşil notlar (▸ Neden işe yarıyor?) Türkçe koçluk notlarıdır.

Sen
Sure. I am backend and platform engineer, around ten years experience. Mostly I work with Go, Kubernetes and cloud. In last years I worked on an identity platform and on a payment backend, so I care a lot about correctness and reliability.
Neden işe yarıyor?20 saniye, üç bilgi: rol, araçlar, neyi önemsediğin. Şirket adı, sayı, hikâye yok; onlar sorulursa gelir.
Interviewer
Nice. So today is about API design and solutions design. We have around 50 minutes.
Sen
Okay. Before we start, can I ask how you want to split the time between design and coding? And which language I can use?
Interviewer
Mostly design. If there's time we might write a bit of code; any language is fine.
Sen
Perfect, then I will use Go if we come to the code.
Neden işe yarıyor?Formatı en başta netleştirmek, zamanı doğru bölmeni sağlar. AI asistan araçta görünüyorsa izni de burada sorabilirsin.
03:00 · Problem
Interviewer
Here's the problem. Our customers want to connect their company tools, like Google Drive and Slack, so our AI agent can answer questions using their documents. Design the API and the backend that keeps these sources in sync and makes the content searchable.
Sen
Okay, nice problem. I like to ask some questions first, if it's okay.
Interviewer
Sure, go ahead.
04:00 · Netleştirme soruları
Sen
Who is using this API? Only admins from the UI, or also other services?
Interviewer
Mainly admins through our UI. And the agent calls search.
Sen
How many customers, and how big is the biggest one? Like, number of documents.
Interviewer
A few hundred enterprise customers. The biggest has around five million documents.
Sen
And how fresh it must be? If someone change a document, how fast we need to see it in search?
Interviewer
Within ten minutes is fine.
Sen
One more, and I think it is the most important: permissions. If a user can not see a document in Drive, he should not see it in our search too, right?
Interviewer
Correct, that's a hard requirement.
Sen
And if someone lose the access, how fast we must remove it?
Interviewer
Good question. Faster than content. A few minutes.
Neden işe yarıyor?Dört soru: kullanıcı, ölçek, tazelik, izin. İzin sorusu bu problemin kalbi; "most important" demen olgunluk gösterir. Soru sayısını 4-5'te tut.
07:00 · Özet ve gereksinimler
Sen
Okay, let me summarize. Admin connects a source, starts a sync and sees the progress. Users search only what they can see. Content should be fresh in ten minutes, permission changes in few minutes, no data leak between customers, and a big customer should not block the small ones. I think the hard part is not QPS. It's permissions, the limits of source APIs, and fairness between customers.
Interviewer
Sounds right. Let's look at the API.
Neden işe yarıyor?Özet, mülakatçıya "doğru problemi çözüyorum" kontrolü verir. Son cümle ("hard part is not QPS") kıdem sinyalidir.
09:00 · API sözleşmesi
Sen
I start with the resources: source, sync, and documents. 
POST   /v1/sources              → 201
POST   /v1/sources/{id}/syncs   → 202 + Location
GET    /v1/syncs/{id}              → status, progress
POST   /v1/search                  → results + source links
DELETE /v1/sources/{id}         → 202 (cleanup is async)
Sync can take hours, so it returns 202 with the sync id. Status is queued, running, succeeded or failed.
Interviewer
Why 202? Why not just do the sync inside the request?
Sen
Because it takes long time. A HTTP request can not wait hours. So the API only saves the job in the database and returns 202. The worker does the real work, and the client can poll the status.
Interviewer
What if the admin clicks "sync" twice, or the client retries after a timeout?
Sen
Every POST has an Idempotency-Key header. If the same key and same body comes again, I return the first response. If same key but different body, I return 409. Also I have a unique index in Postgres, only one active sync per source. So even two different requests can not start two syncs.
Interviewer
And how do you know which customer the request belongs to?
Sen
From the token. The gateway checks the JWT, and the tenant comes from there, never from the request body. And every table has tenant_id.
Neden işe yarıyor?Retry sorusuna iki katmanlı cevap: uygulamada idempotency key, veritabanında unique index. "Never from the body" cümlesi güvenlik farkındalığı gösterir.
17:00 · Basit v1 mimari
Interviewer
Let's talk about the architecture.
Sen
I will draw first a simple version. Admin goes to the gateway, for JWT and rate limit, then to the Knowledge Sources API. The API is stateless. It writes to Postgres: in the same transaction, the sync row and a pending_events row. An event publisher sends it to a Kafka topic, and a sync worker takes it. This is the simplest version that works. Where you want me to go deeper?
Interviewer
Why Kafka already in the first version? Wouldn't a table in Postgres be enough?
Sen
For only the sync jobs, yes, a Postgres table is enough. But this is a pipeline of events: sync jobs now, and later the change events from webhooks and the permission changes go the same way. One big new tenant can make hundreds of thousands of document events in few hours, and I don't want this load on the main Postgres that serves the API. Kafka keeps them, spreads them to the workers, and with source id as key, one source is processed in order. We can also replay a topic if a consumer had a bug.
Neden işe yarıyor?Önce dürüstçe "sadece sync işleri için Postgres yeterdi" de, sonra bu sistemin bir olay hattı olduğunu söyle. Kararı ihtiyaca bağlıyorsun; ezberden "Kafka koyalım" demiyorsun. Ayrıntı
Interviewer
Why the pending_events table?
Sen
If I write to the database and then publish to the queue, and the service crash between them, the job is saved but nobody does it. With pending_events both are in one transaction. The event publisher can publish twice, but the worker is idempotent, so it's fine.
Interviewer
What does the worker actually do?
Sen
It calls the source API with a cursor, like "give me the changes since last time", page by page. After each page I save the cursor, so after a crash it continues from there. For each document I check the hash. If content is same, I skip it. Then I upsert the document and its ACL into Postgres.
Neden işe yarıyor?Önce 5 kutuluk v1, sonra "nereye derinleşeyim?" sorusu. Kontrolü mülakatçıya vermek, fazla karmaşık tasarım tuzağından korur. Bkz. Diyagram A, aşama 1-2.
24:00 · Hata senaryoları
Interviewer
What happens if the worker crashes in the middle of a page?
Sen
Then it doesn't commit the offset, so Kafka gives the message again to the worker that takes over the partition. Because the upsert is idempotent, processing the same page again gives the same result. The cursor was not moved yet, so nothing is lost.
Interviewer
Okay. Now our biggest customer, five million documents, connects on a Monday morning. What happens?
Sen
Hmm, this is the noisy neighbor problem. If everything is in one queue, small customers wait behind. So I make two lanes: one for the initial import, and one for live changes. And I limit how many workers one customer can use at same time. The source API also has quota, so I keep a token bucket in Redis per customer and per source.
Interviewer
And if Google starts returning 429s?
Sen
I respect the Retry-After and put the message back with a delay, not let the worker sleep. And a circuit breaker per source, so if Slack is down, Drive sync still works.
Neden işe yarıyor?"Hmm" ile düşünmek sorun değil. Problemi adlandırmak ("noisy neighbor") ve iki somut çözüm (iki şerit, tenant limiti) vermek yeterli.
31:00 · İzinler
Interviewer
Let's go back to permissions. A user is removed from a group in Drive. Walk me through it.
Sen
For me this is the most important path. Permission changes go to a separate priority queue, so they don't wait behind the big import. The ACL worker updates the ACL table; no need to embed again. In search, I filter by permission first and rank after. If I don't know the permission, I don't show the document. Fail closed.
Interviewer
Why filter first and not after ranking?
Sen
If I filter after, maybe the top ten results are all not allowed, and I return nothing. Or worse, there is a risk to leak something in the snippets. Filtering first is safer.
Interviewer
Makes sense. How do you know which groups the user is in?
Sen
From the identity provider or the source, and I cache it in Redis for a short time, like five minutes. That five minutes is the trade-off. If the business wants faster, I make the TTL smaller, or check directly for sensitive documents.
Neden işe yarıyor?Trade-off'u kendin söylemek ("that five minutes is the trade-off") en güçlü kıdem sinyallerinden biri. Mülakatçının yakalamasını bekleme.
39:00 · Production
Interviewer
How would you run this in production?
Sen
On Kubernetes. The API scales with HPA, and the workers scale with the queue backlog, with KEDA. For SLOs I would say: API availability 99.9, freshness ten minutes at p95, permission removal under five minutes. I alert on the age of the oldest message, the DLQ rate and the 429 rate per source, not on CPU. And I deploy with canary, so if the error rate goes up, we roll back.
Interviewer
If you had more time, what would you add?
Sen
Two things. Embeddings for semantic search, but only when the content changes, because it cost money. And a reconciliation job that compares ACLs with the source once a day, because webhooks can get lost.
Neden işe yarıyor?Infra rolü için operasyon kısmı senin güçlü alanın: semptoma göre alarm (en eski mesajın yaşı), canary, SLO. Kısa ve somut tut.
45:00 · Senin soruların
Interviewer
Great, we're almost at time. Do you have any questions for me?
Sen
Yes, two questions. What is the biggest reliability problem in the platform right now? And how does the infra team work with feature teams, is it more building tools, or more hands-on support?
Interviewer
Good questions. Right now it's mostly dependencies on model providers and knowledge sync at scale. And it's a mix: we build the paved road, but we also pair with teams on launches.
Sen
That sounds interesting, thank you. It was a nice discussion.
Interviewer
Thank you too. Our recruiter will be in touch about next steps.
Neden işe yarıyor?İki soru yeter. Rolün gerçek işini soran sorular ilgi gösterir. Bitirirken "What are the next steps?" sorusunu recruiter'a sakla.
