Genel takip soruları

Mülakatçılar senaryodan bağımsız bu tür sorularla derinleşir. Her soru için Türkçe ana fikir ve 2-3 cümlelik basit İngilizce cevap.

Nasıl çalışılır? Soruyu oku, açmadan önce 20 saniyede kendi cevabını sesli söyle, sonra aç ve karşılaştır. Cevapları ezberleme; ana fikri ve bir örneği hatırla.

API

1. How do you version this API?

Ana fikir: Versiyon URL'de; ek alan kırmaz, silmek/anlam değiştirmek kırar.

I put the major version in the URL, like /v1. Adding a new field is safe, but removing a field or changing its meaning is a breaking change, so that goes to /v2. I run both versions for a while, send deprecation headers, and check usage before I remove the old one.
2. How do you paginate large lists?

Ana fikir: Offset değil cursor.

With a cursor, not offset. The cursor is an opaque token with the last sort key, so it stays fast on big tables and doesn't skip items when new rows are added. And I always set a maximum page size.

3. How do you handle errors in the API?

Ana fikir: Tek hata formatı, makine için sabit kod, request id.

One error format for the whole API, with a stable machine-readable code, a human message and a request id that matches our logs. 4xx means the client can fix it, 5xx or 503 with Retry-After means it can try again later.

Veri ve ölçek

4. Why Postgres and not a vector database from day one?

Ana fikir: Bilinen tek sistem; gerçek bir sınır görünce taşı.

The team already runs Postgres well, and one system is easier to operate. With pgvector it's fine for the start. When a big tenant makes the index too large or too slow, I move that part to a dedicated vector store, but I want a real reason first.
5. Why Kafka here?

Ana fikir: Key başına sıra, replay, yüksek hacim; bedeli işletme ve retry/DLT'yi kendin kurmak. Sözlük →

Kafka gives us ordering per key, so all changes for one source or task stay in order, and we can replay a topic if a consumer had a bug. The cost is operations and that retries and dead-letter topics are our job, so I'd use a managed Kafka. For a small team, a simpler managed queue would also work.
6. One big tenant is slowing everyone down. What do you do?

Ana fikir: Tenant limiti, ayrı şeritler, adil sıralama.

That's the noisy neighbor problem. I add per-tenant limits on workers and rate, separate lanes for big imports and live traffic, and fair scheduling between tenants. And I measure lag per tenant, so we see it before customers complain.
7. EU customer data must stay in the EU. What changes?

Ana fikir: Bölge başına hücre, tenant→bölge eşlemesi, modelin de bölgede olması.

I deploy one cell per region, with its own database, queue and storage, and map every tenant to a home region. Content never replicates to another region. And the model provider must also be in that region, including the fallback model.

Güvenilirlik ve operasyon

8. How do you change the database schema without downtime?

Ana fikir: Expand → backfill → contract.

Expand, backfill, contract. First I add the new column or table in a backward-compatible way, then backfill in small batches, then switch the code, and only at the end remove the old part. Indexes with CREATE INDEX CONCURRENTLY and a lock timeout on migrations.
9. The primary database fails over. What do users see?

Ana fikir: 30-60 sn yazma hatası; retry güvenli çünkü idempotent.

Around thirty to sixty seconds of write errors. The API returns 503 with Retry-After, workers retry with backoff, and reads can continue from a replica. Because writes are idempotent, the retries are safe.
10. How do you deploy safely?

Ana fikir: Canary + metriğe bağlı otomatik rollback; deploy ≠ release.

Canary first, to a small part of the traffic, and automatic rollback if error rate or latency goes up. Risky features stay behind a feature flag, so deploy and release are two different steps.
11. What would you monitor first?

Ana fikir: Kullanıcının hissettiği semptomlar; SLO burn rate alarmı.

The symptoms users feel: error rate, latency, the age of the oldest message in the queue, and data freshness. I alert on SLO burn rate, not on CPU. CPU is useful for debugging, not for paging someone at night.
12. The LLM provider is down for an hour. What happens?

Ana fikir: Circuit breaker, fallback, kademeli düşüş.

A circuit breaker stops us from hammering it. We fall back to another model if it's allowed for the customer's region. If nothing works, we degrade: search still returns documents without a generated answer, and async tasks wait in the queue.
13. How would you test this system?

Ana fikir: Fake'li unit, contract, gerçek Postgres'li entegrasyon, worker öldürme.

Unit tests with fakes for the storage and the clock, contract tests from the OpenAPI spec, integration tests with a real Postgres in a container, and some chaos tests, like killing a worker in the middle of a sync and checking nothing is lost or duplicated.

Güvenlik

14. How do you make sure one tenant never sees another tenant's data?

Ana fikir: Tenant token'dan; her yerde tenant_id; RLS ikinci katman; test.

The tenant comes from the verified token, never from the request. Every table and every query has tenant_id, and row-level security is a second layer. And we have tests that call with tenant A's token for tenant B's object and expect a 404.
15. Tokens are stateless. How do you revoke access quickly?

Ana fikir: Kısa ömür + refresh iptali; kritik işlerde merkezi kontrol.

Short-lived access tokens, a few minutes, and we revoke the refresh token on logout or when a user is disabled. So the worst case is the token lifetime. For very sensitive actions I check a central service at that moment. That's a trade-off between speed and how fast revocation must be.
16. How would you design rate limiting?

Ana fikir: Redis token bucket; okuma fail-open, pahalı işler fail-closed.

A token bucket in Redis, updated atomically, per API key and per tenant, plus a small local limit in each pod. If Redis is down, I fail open for cheap reads but fail closed for expensive things like LLM calls.

AI ve maliyet

17. How do you estimate and control LLM cost?

Ana fikir: Task başına token × task sayısı; tenant bütçesi; değişmeyeni işleme.

Tokens per task times tasks per day gives the rough number, and in our case the model is the biggest cost, not CPU. I control it with a token budget per tenant, by not re-embedding content that didn't change, and by measuring cost per tenant on a dashboard.
18. How do you deal with prompt injection?

Ana fikir: Çıktı = güvenilmez veri; kullanıcı yetkisi; yazan aksiyona onay.

I treat any text from documents or tools as untrusted data, not instructions. Tools run with the user's own permissions, so the agent can't access more than the user. And actions that write need approval for the exact parameters.
