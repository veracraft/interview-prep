Diğer sorular: neyi farklı yapardın?

Seçmediğin yedi soru. Her biri hazırladığın en yakın soruyla karşılaştırılıyor: ne aynı kalıyor, ne değişiyor, API taslağı, tuzak ve açılış cümlesi. Başlığa dokun, açılsın.

Genel kural: playbook aynı (kapsam → API → minimum çözüm → hata → ölçek). Değişen, darboğazın nerede olduğu: okuma ağırlıklıda cache ve tutarlılık; yazma ağırlıklıda kabul, tekrar ve toplama; dışarıya yazanda karşı tarafın hataları.
Bu sayfada

  2. Yazma ağırlıklı: audit log, geri bildirim

Okuma ağırlıklı (en yakını: feature flag)

Model kataloğu API'si · en yakını: Feature flag servisi
Design the API that lists available models, their prices and limits.

Hazırladığın en yakın soru: Feature flag servisi. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanOkuma ağırlıklı; cache + ETag; yazma nadir ve sürümlü.
Farklı yapacakların
  • Okuyan iç servisler değil, herkes (müşteriler, SDK'lar, doküman sitesi). SDK'da kopya yerine HTTP cache: CDN + Cache-Control: public, max-age=300 + ETag.
  • Ortak ve kişiye özel veriyi ayır: katalog herkese aynı (CDN'de cache'lenir); tenant'a özel fiyat ve limit ayrı endpoint'te, Cache-Control: private, no-store.
  • Fiyat değişikliği ileri tarihli: effective_from. Cache'teki eski fiyat fatura hatası yaratmaz, çünkü fatura sunucuda hesaplanır; bunu söyle.
  • Model emekliliği: deprecated_at, Sunset header'ı; istemcilere önceden haber.
TuzakKişiye özel cevabı CDN'e cache'letmek: bir müşteri başka müşterinin limitini görür.
API taslağı
GET /v1/models                 → public, CDN
GET /v1/models/{id}
GET /v1/me/limits               → private, tenant'a özel
PUT /v1/models/{id}             → iç, nadir (If-Match)
This is read-heavy and mostly public, so I'll lean on HTTP caching: a CDN with ETags for the shared catalog, and a separate private endpoint for tenant-specific prices and limits.
URL kısaltıcı · en yakını: Feature flag servisi
Design a URL shortener.

Hazırladığın en yakın soru: Feature flag servisi. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanOkuma ağırlıklı; sıcak okuma yolu cache'ten.
Farklı yapacakların
  • Kod üretimi asıl soru: rastgele 7 karakter base62 (≈3,5 trilyon ihtimal) + unique index; çakışırsa yeniden üret. Sıralı sayaç tahmin edilebilir: herkes tüm linkleri gezebilir.
  • Yönlendirme milisaniyeler içinde: GET /{code} → kod → URL cache'ten (Redis ya da CDN).
  • 301 mi 302 mi: 301'i tarayıcı kalıcı cache'ler, sonraki tıklamaları göremezsin; istatistik isteniyorsa 302.
  • Tıklama sayımı ayrı, yazma ağırlıklı bir yol: olay kuyruğa asenkron; yönlendirmeyi bekletmez (usage metering'e benzer).
  • Kötüye kullanım: zararlı URL taraması, link oluşturmada rate limit.
TuzakSıralı kod (enumeration); 301 yüzünden istatistiğin kaybolması.
API taslağı
POST   /v1/links        { url, custom_alias?, expires_at? } → 201 { code }
GET    /{code}          → 302 Location: <url>
GET    /v1/links/{code}/stats
DELETE /v1/links/{code}
There are two separate paths: a small write path that generates a unique random code, and a hot read path that must redirect in a few milliseconds from cache. Click counting goes async so it never slows the redirect.

Yazma ağırlıklı (en yakını: usage metering)

Audit log · en yakını: Usage metering
Design an audit log that our services write to and enterprise customers can query and export.

Hazırladığın en yakın soru: Usage metering. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanYüksek yazma; toplu gönderim; Kafka; ana isteği yavaşlatmamak; event_id ile tekrar yok; sütun tabanlı, gün bazında bölümlü depo.
Farklı yapacakların
  • Toplama yok: her olay tek tek önemli ve değiştirilemez. Silme ve güncelleme endpoint'i yok; append-only depo, gerekirse hash zinciri ya da WORM bucket.
  • Kaybetmek kabul edilemez: olay, eylemle aynı transaction'da pending_events'e yazılır (usage'da gateway tamponu yeterliydi).
  • Okuma filtreli: actor, action, zaman aralığı + cursor. Büyük dışa aktarma async: 202 + export işi + indirme linki.
  • Saklama tenant ayarı (1–7 yıl); kişisel veriyi azalt ya da maskele (GDPR ile çatışmasın).
  • Sadece tenant admin ve denetçi okur; audit log'u okumak da audit'lenir.
TuzakAudit'i ana isteğin içinde senkron yazmak (yavaşlatır) ya da "gönder ve unut" (kaybolur). Doğrusu: aynı transaction'da pending_events.
API taslağı
POST /v1/audit-events:batch                   → iç servisler
GET  /v1/audit-events?actor=&action=&from=&to=&cursor=
POST /v1/audit-exports  { from, to, format } → 202
GET  /v1/audit-exports/{id}                    → durum + indirme linki
Audit events are write-heavy like usage, but there's no aggregation: every event matters and must be immutable. I'll write them through pending_events in the same transaction as the action, keep append-only storage, and make exports async.
Geri bildirim (👍/👎) · en yakını: Usage metering
Users can rate an agent's answer with thumbs up or down and an optional comment. Design the API.

Hazırladığın en yakın soru: Usage metering. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanYazma odaklı; tenant izolasyonu.
Farklı yapacakların
  • Hacim küçük: Kafka, ham depo, aggregator gerekmez. Tek Postgres tablosu.
  • Doğal idempotency: PUT /v1/messages/{id}/feedback; kullanıcı + mesaj başına tek kayıt. Fikir değiştirirse üzerine yazar, DELETE ile geri alır. Idempotency-Key gereksiz.
  • Analiz için günlük toplam: gece çalışan bir sorgu ya da materialized view.
  • Yorum metni kişisel veri içerebilir: saklama süresi ve erişim.
TuzakBasit soruya Kafka ve Redis eklemek: "neden?" sorusuna cevap veremezsin.
API taslağı
PUT    /v1/messages/{id}/feedback  { rating: "up" | "down", comment? } → 200
DELETE /v1/messages/{id}/feedback  → 204
GET    /v1/feedback/summary?agent_id=&from=&to=
This is small, so I'll keep it simple: one table, and PUT on the message's feedback gives me idempotency for free. A user can change their mind by overwriting it.

Diğer (en yakını: API key yönetimi)

Webhook teslim servisi · en yakını: API key yönetimi
Customers register URLs and we send them events. Design it.

Hazırladığın en yakın soru: API key yönetimi. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanSecret bir kez gösterilir ve rotate'te bir süre iki secret birlikte geçerli (API key'lerdeki gibi).
Farklı yapacakların
  • Kontrol etmediğin sunuculara yazıyorsun: müşteri sunucusu yavaş ya da kapalı olabilir. Teslim en az bir kez (at-least-once); alıcı event_id ile tekilleştirir, bunu dokümante et.
  • Retry: üstel bekleme + jitter, ~24 saat; sonra dead-letter, endpoint'i kapat ve müşteriye e-posta.
  • Bir müşteri diğerlerini bekletmesin: endpoint başına eşzamanlılık sınırı ve circuit breaker; timeout 10 sn.
  • Güvenlik: HMAC imza + zaman damgası (replay'e karşı); iç IP'lere gönderme yok (SSRF).
  • Sıra garanti değil; gerekiyorsa olayda sıra numarası.
TuzakTek ortak kuyrukta yavaş bir müşterinin herkesi tıkaması; imzasız webhook; iç ağa istek atılması.
API taslağı
POST /v1/webhooks                   { url, events[] } → 201 { id, secret }   (secret bir kez)
GET  /v1/webhooks/{id}/deliveries?cursor=
POST /v1/deliveries/{id}:retry
POST /v1/webhooks/{id}:rotate-secret
We send events to servers we don't control, so I design for them being slow or down: at-least-once delivery with backoff, per-endpoint isolation so one bad customer can't block others, and signed payloads.
Rate limiter · en yakını: API key yönetimi
Design rate limiting for our public API.

Hazırladığın en yakın soru: API key yönetimi. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanGateway'de, key ve tenant bazında; Redis'te ortak sayaç (API key sayfasındaki follow-up).
Farklı yapacakların
  • API değil algoritma ve yerleşim sorusu. Token bucket öner: kısa ani yüke izin verir, ortalamayı sınırlar. Sabit pencere kenarlarda iki kat geçirir; kayan pencere doğru ama pahalı.
  • Dağıtık sayaç: Redis'te atomik (Lua) bir işlem; ya da pod başına yerel limit (limit / pod sayısı): yaklaşık ama Redis'siz.
  • Redis çökerse: genel limitlerde fail open (yerel limite düş), çünkü limiter yüzünden bütün API düşmemeli; giriş denemesi gibi güvenlik limitlerinde fail closed.
  • Cevap: 429 + Retry-After + RateLimit-Limit/Remaining/Reset header'ları.
  • Katmanlar: tenant'ın plan limiti, pahalı endpoint'e ayrı limit, genel koruma.
TuzakHer istekte veritabanına gitmek; Redis çökünce "fail closed" ile bütün API'yi düşürmek.
API taslağı
Her cevapta:
  RateLimit-Limit: 600
  RateLimit-Remaining: 12
  RateLimit-Reset: 18

429 Too Many Requests
Retry-After: 18

GET /v1/limits   → müşteri kendi limitlerini görür
I'd use a token bucket per tenant and per key at the gateway, with counters in Redis updated atomically. If Redis is down I fall back to a local per-pod limit, because the limiter shouldn't take the whole API down.
Dosya yükleme API'si · en yakını: API key yönetimi
Users upload files up to 2 GB for the agent to use. Design the API.

Hazırladığın en yakın soru: API key yönetimi. Oradaki akışı kullan; aşağıdakileri değiştir.

Aynı kalanKısa ömürlü, tek amaçlı kimlik bilgisi (presigned URL, API key'e benzer şekilde süreli ve kapsamlı); uzun iş için 202 + durum (Knowledge Sync'teki gibi).
Farklı yapacakların
  • Büyük veri API'den geçmesin: API bir presigned URL verir, istemci doğrudan object storage'a (S3, GCS) yükler; büyük dosyada multipart ve kaldığı yerden devam.
  • Bitince haber: :complete → 202; arka planda virüs taraması, tür kontrolü, metin çıkarma. Durum: uploading → scanning → ready | rejected.
  • Yarım kalanlar: storage lifecycle kuralı 24 saat sonra siler.
  • Sınırlar: boyut, tür (uzantı değil içerik), tenant kotası.
  • İndirme: kısa ömürlü presigned GET; yetki her seferinde kontrol edilir.
Tuzak2 GB'ı API pod'undan geçirmek; dosyayı tarama bitmeden kullanılabilir yapmak.
API taslağı
POST /v1/files              { name, size, content_type } → 201 { id, upload_url, expires_at }
PUT  <upload_url>           → doğrudan storage'a
POST /v1/files/{id}:complete → 202
GET  /v1/files/{id}          → { status: "scanning" | "ready" | "rejected" }
GET  /v1/files/{id}/content  → 302 presigned URL
Large files shouldn't go through our API. The API hands out a presigned URL, the client uploads straight to object storage, and processing like virus scanning happens async with a status the client can poll.
