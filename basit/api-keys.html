API key yönetimi

Güvenlik odaklı basit bir soru. Yönetim tarafı basit bir CRUD; asıl tasarım sorusu her istekteki doğrulama.

1 · Kapsam

Playbook 1/5 · Kapsam. kim kullanıyor, ana işlem ne, veri ne büyüklükte, ne kadar güncel olmalı? 5 dakikayı geçme.
Customers call our public API with API keys. Design the API to create, list, rotate and revoke keys, and how every request is authenticated with them.
SorVarsayılan cevapNeyi değiştirir?
Kim yönetir?Tenant admin'i, panelden ya da API'den.Yönetim yetkisi bir rol.
Kaç key, kaç istek?Tenant başına ~10 key; public API saniyede 50k istek.Doğrulama her istekte: çok hızlı olmalı.
Key'in yetkisi?Kapsamlı (scope), ör. tasks:write; isteğe bağlı son kullanma tarihi.scopes ve expires_at.
İptal ne kadar hızlı yansımalı?Sızan key 1 dakika içinde çalışmamalı.Cache süresi kısa.
Rotation?Kesintisiz: yeni key oluştur, eskisi bir süre daha çalışsın.İki key aynı anda geçerli.

FonksiyonelOluştur (secret bir kez görünür) · listele (secret'sız) · döndür (rotate) · iptal · son kullanım zamanı.
Fonksiyonel olmayanDoğrulama p99 < 5 ms · iptal p99 < 60 sn · key'ler asla düz metin saklanmaz · doğrulama %99.99 (her istek ona bağlı).
Kaba ölçek500 tenant × 10 = 5.000 key · yönetim çağrısı günde birkaç yüz · doğrulama saniyede 50k.

Çıkarım: yönetim API'si basit bir CRUD. Asıl soru her istekte yapılan doğrulama: hızlı, güvenli ve iptale duyarlı.

The management API is simple CRUD. The real design question is verification on every request: we store only a hash, the gateway checks it against a short-lived cache, and a revoked key stops working within a minute.

2 · API sözleşmesi

Playbook 2/5 · API sözleşmesi. endpoint'ler → bir tam request/response → hatalar. Idempotency ve yetkiyi burada söyle.

Endpoint'e ya da hata koduna tıkla: altında istek ve cevap açılır. ↗ işaretli hücre ilgili karara götürür.

Kaynak: api key. Key'in şekli: sk_live_k7Qp2_9aFh… = önek + key id + rastgele secret. Önek key'i tanıtır, secret doğrular.

İstekNe demek, neden?
POST /v1/api-keysYeni bir key oluştur.
Authorization: Bearer <admin JWT>Kim olduğun: tenant ve rol token'dan. Sadece admin key oluşturabilir; bir API key başka key oluşturamaz.
Idempotency-Key: 3e8a…Ağ koparsa tekrar gönderilir; ikinci bir key oluşmaz. Ama secret'ı saklamadığımız için tekrar gelen isteğe secret'sız aynı key döner (aşağıda karar k5).
"scopes": ["tasks:write"]Bu key ne yapabilir. En az yetki: CI'ın key'i sadece task oluşturabilsin.
"expires_at": "2027-06-01…"İsteğe bağlı son kullanma tarihi. Sonsuz key'ler en büyük risk.
CevapNe demek, neden?
201 CreatedKey hemen kullanılabilir. 202 değil, çünkü arka planda iş yok.
"key": "sk_live_k7Qp2_9aFhT3…"Secret'ın tek gösterimi. Biz sadece SHA-256 hash'ini saklıyoruz; kaybedilirse geri getirilemez.
"prefix": "sk_live_k7Qp2"Listede key'i tanımak için. sk_live_ öneki, GitHub gibi tarayıcıların sızan key'i tanımasını da sağlar.
Authorization: Bearer sk_live_k7Qp2_9aFhT3…

1. önekten key id'yi ayır                → key_k7Qp2
2. gateway'in belleğinde (60 sn) var mı? → yoksa Postgres'ten id ile oku
3. sha256(secret) == secret_hash ?        (sabit zamanlı karşılaştırma)
4. status active, süresi dolmamış, scope bu endpoint'e yetiyor mu?
5. isteğe tenant'ı ekle (X-Tenant-Id: ten_42), backend'e ilet
6. last_used_at'i arka planda, dakikada bir güncelle

SHA-256 yeter, bcrypt gerekmez: secret 256 bit rastgele bir değer, parola değil; kaba kuvvetle kırılamaz. bcrypt saniyede 50k istekte çok yavaş olurdu.

Tek hata formatı: sabit code, message, request_id. 401 mesajı hep aynı: "yanlış", "iptal", "süresi dolmuş" ayrımı saldırgana bilgi verir.

We show the secret once, store only its hash, and verify every request at the gateway against a short-lived cache, so revocation takes effect within a minute.

4 · Hata ve güvenlik

Playbook 4/5 · Hata ve güvenlik. her cevap: karar → gerekçe → bedel.
SoruKararGerekçeBedel / alternatif
How do you store the secret?Sadece SHA-256 hash'i; düz metin hiçbir yerde (log'lar dahil). Secret bir kez gösterilir.Veritabanı sızarsa key'ler kullanılamaz.Kaybedilen key geri getirilemez; yenisi oluşturulur. bcrypt gerekmez: secret rastgele ve uzun.
How is verification fast on every request?Önekten key id → gateway belleği (60 sn) → yoksa Postgres'te tek satır (PK). Hash sabit zamanlı karşılaştırılır.Saniyede 50k istek; her biri veritabanına gidemez.İptal 60 sn gecikebilir.
How fast does revocation take effect?Minimum: bellek süresi kadar, en geç 60 sn. Daha hızlı gerekirse iptal olayı pub/sub ile her gateway'e gider ve bellekten silinir.Sızan key bir dakikadan uzun çalışmamalı.Süreyi kısaltmak veritabanı yükünü artırır; pub/sub bir parça daha.
How do you rotate without downtime?:rotate yeni key oluşturur; eskisi süre boyunca (ör. 24 saat) çalışır, sonra kendiliğinden kapanır.Müşteri yeni key'i deploy edene kadar istekleri kesilmemeli.Bir süre iki key birlikte geçerli (risk penceresi).
What if the create request is retried?Idempotency-Key ile ikinci key oluşmaz; ama aynı key secret'sız döner. Müşteri secret'ı kaybettiyse key'i iptal edip yenisini oluşturur.Secret'ı saklamıyoruz; ikinci kez gösteremeyiz.Nadiren yeni key oluşturmak gerekir.
Who may manage keys?Tenant admin rolü; bir API key başka key oluşturamaz; her işlem audit log'da.Sızan bir key kendine yeni key'ler üretip kalıcı hale gelmemeli.Basit bir rol modeli.
How do you detect a leaked key?sk_live_ öneki sayesinde GitHub gibi tarayıcılar sızan key'i tanır ve bize bildirir → otomatik iptal + e-posta. 401 oranındaki ani artışa alarm.Key'ler kod depolarına sızar; hızlı fark etmek gerek.Tarayıcı entegrasyonu.
Why is every 401 the same?"Yanlış", "iptal", "süresi dolmuş" ayrımı sadece müşterinin kendi panelinde ve log'larda; API cevabı hep aynı.Saldırgan hangi key'lerin bir zamanlar geçerli olduğunu öğrenmemeli.Müşterinin hata ayıklaması biraz zorlaşır; panelde last_used_at ve durum yardım eder.
How do we know it's healthy?Doğrulama gecikmesi (p99), bellek isabet oranı, 401 oranı (ani artış = sızıntı ya da saldırı), iptalin yayılma süresi.Doğrulama her isteğin önünde; yavaşlarsa her şey yavaşlar.Metrikler gateway'den gelmeli.

5 · Ölçek ve follow-up

Playbook 5/5 · Ölçek ve follow-up. önce darboğazı adlandır, sonra parçayı ekle.

Önce soruyu oku, 20 saniyede kendi cevabını sesli söyle, sonra aç.

1. Revocation must be instant.

Ana fikir: Pub/sub ile anında bellekten silme (3. aşama); ek olarak kısa süreli "iptal edildi" kaydı.

When a key is revoked, the Keys API publishes an event and every gateway drops it from its cache right away. The 60-second expiry stays as a safety net in case a message is lost.
2. Postgres is down. Can requests still be authenticated?

Ana fikir: Bellekteki key'ler çalışmaya devam eder (stale-if-error); bilinmeyen key reddedilir.

Keys already in the gateway cache keep working for a while even if Postgres is down, and unknown keys are rejected. That's fail-open for known keys and fail-closed for unknown ones, a trade-off I'd say explicitly.
3. Why not JWTs instead of API keys?

Ana fikir: JWT kısa ömürlü ve iptali zor; API key uzun ömürlü ve iptal edilebilir. İkisi birlikte: key ile kısa ömürlü token alınır (OAuth client credentials).

JWTs are short-lived and hard to revoke, API keys are long-lived and revocable. For high traffic I can combine them: the client exchanges the key for a short-lived token, OAuth client-credentials style.
4. Each key needs its own rate limit.

Ana fikir: Gateway'de key id başına token bucket (Redis).

The gateway already knows the key id, so I add a token bucket per key in Redis, on top of the per-tenant limit.

Parçalar

Diyagramdaki kutuya tıklayınca buraya gelirsin: her parça için hangi problemi çözdüğü, neden şimdi gerektiği ve daha basit alternatifi.

Gateway #

Her istekte key'i doğrular: önek, bellek, hash, durum, scope. Yönetim isteklerinde de admin JWT'sini doğrular.

Hangi problemi çözüyor? Doğrulamayı her serviste tekrar yazmamak; tek yerde, hızlı.
Neden şimdi? 1. aşama.
Daha basit alternatif: Her servisin key'i kendisinin doğrulaması.
Bedeli: Kritik yolda; yavaşlarsa her şey yavaşlar.

Keys API #

Key oluşturur, listeler, döndürür, iptal eder. Secret'ı üretir, sadece hash'ini yazar.

Hangi problemi çözüyor? Key yaşam döngüsünü tek yerde ve audit'li yönetmek.
Neden şimdi? 1. aşama.
Daha basit alternatif: Panelin doğrudan veritabanına yazması.
Bedeli: Bir servis daha.

Postgres #

api_keys tablosu: hash, tenant, scope, durum, son kullanım.

Hangi problemi çözüyor? Kalıcı ve doğru durum; id ile hızlı okuma.
Neden şimdi? 1. aşama.
Daha basit alternatif: Bu zaten en basit seçenek.
Bedeli: Okuma yükünü bellek karşılıyor.

Key cache (gateway belleği) #

Her gateway pod'unda, key id → hash, tenant, scope; 60 sn tutulur.

Hangi problemi çözüyor? Saniyede 50k doğrulamanın veritabanına gitmemesi.
Neden şimdi? 2. aşama.
Daha basit alternatif: Her istekte Postgres'e gitmek.
Bedeli: İptal 60 sn gecikebilir; follow-up'ta pub/sub ile anında silinir.
