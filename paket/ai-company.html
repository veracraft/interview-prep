API aşaması

Let me start with the resources and the contract, because the contract is the hardest thing to change later.

This operation can take minutes, so instead of holding the request open I'll return 202 with an operation resource the client can poll, plus an optional webhook.

Clients will retry, so every mutating call accepts an Idempotency-Key.

Mimari / trade-off

I'll keep the API layer stateless so we can scale it horizontally with an HPA, and push the heavy work to async workers.

The trade-off here is eventual consistency: the user sees the change within a few seconds instead of immediately. For this use case that's acceptable, but not for permissions.

I'd start with Postgres because it's what the team already runs well; I'd only move to something else when we hit a concrete limit.

API tasarımı kopya kağıdı3 / 15 · Ezberle

1. Kaynak odaklı URL'ler

GET    /v1/sources?cursor=..&limit=50   list
POST   /v1/sources                        create → 201 + Location
GET    /v1/sources/{id}                   read
PATCH  /v1/sources/{id}                   partial update
DELETE /v1/sources/{id}                   → 204 (veya 202 async)
POST   /v1/sources/{id}/syncs             alt kaynak (sub-resource)
POST   /v1/tasks/{id}:cancel                  aksiyon (Google AIP stili)

İsimler çoğul, fiil yok. Aksiyon şart ise :cancel veya /cancel. Tenant'ı URL'e koyma, token'dan çıkar (spoofing riski yok).

3. Hata formatı (RFC 9457 problem+json)

{ "type": "https://api.example.com/errors/quota-exceeded",
  "title": "Token quota exceeded",
  "status": 429,
  "detail": "Tenant t_42 used 100% of daily tokens",
  "code": "QUOTA_EXCEEDED",        // makine için sabit
  "request_id": "req_9f1c",        // log/trace ile eşleşir
  "errors": [{"field":"limit","msg":"max 100"}] }

4. Sayfalama: cursor (offset değil)

GET /v1/documents?limit=50&cursor=eyJpZCI6...
→ { "data": [...], "next_cursor": "eyJ...", "has_more": true }
SQL: WHERE (created_at, id) < ($1, $2)
     ORDER BY created_at DESC, id DESC LIMIT 51

Offset büyük tablolarda yavaş ve araya ekleme olunca kayar. Cursor = opak, base64 (son sıralama anahtarı). Limit'e üst sınır koy.

5. Idempotency

POST /v1/syncs
Idempotency-Key: 7c1e-...  (istemci üretir, UUID)
1) (tenant, key) ara → varsa: aynı hash ise kayıtlı
   cevabı dön; farklı payload ise 409
2) yoksa: INSERT ... (UNIQUE tenant_id, key)
3) işi yap, cevabı kaydet (TTL 24 saat)

PUT/DELETE zaten idempotent. Ağ hatasında istemci aynı key ile exponential backoff + jitter ile tekrar dener.

6. Uzun süren işler (LRO)

POST /v1/sources/c1/syncs → 202
Location: /v1/syncs/s_77
{ "id":"s_77", "status":"queued" }
GET /v1/syncs/s_77 → {status:"running", progress:{done:1200,total:5000}}
Durumlar: queued → running → succeeded | failed | cancelled

Polling + opsiyonel webhook (HMAC imzalı) veya SSE stream. LLM çıktısı için SSE.

7. Eşzamanlı güncelleme

ETag: "v12" → istemci If-Match: "v12" ile PATCH. Uyuşmazsa 412. DB'de UPDATE … WHERE id=$1 AND version=$2 (optimistic locking).

8. Auth

  • Kullanıcı: OIDC (Auth Code + PKCE) → kısa ömürlü JWT access token. Servis lokal JWKS ile doğrular (kurumsal IAM'de olduğu gibi).
  • Makine/entegrasyon: OAuth2 client credentials veya API key (DB'de hash'i, prefix ile tanınır: sk_live_ab12…), scope'lar.
  • Authz: token'da kaba roller; ince izin servis içinde. Her sorguda tenant_id filtresi + Postgres RLS.

9. Rate limit başlıkları

429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 600   RateLimit-Remaining: 0   RateLimit-Reset: 12

Token bucket (Redis + Lua, atomik). Boyutlar: tenant, kullanıcı, API key, endpoint. LLM için token bazlı bütçe.

10. Versiyonlama ve evrim

  • URL'de major: /v1. Ek alan eklemek kırmaz; alan silmek, anlam değiştirmek, zorunlu alan eklemek kırar.
  • İstemciler bilinmeyen alanları yok saymalı (tolerant reader). Enum'a değer eklemek dikkat ister.
  • Deprecation: Deprecation + Sunset header, kullanım metrikleri, iletişim.
  • Sözleşme önce: OpenAPI spec → codegen, contract test, lint (Spectral) CI'da. (DX cümlesi!)

11. Diğer kontrol listesi

Request ID / trace header (traceparent) · max body size · zaman ISO-8601 UTC · para integer · ID'ler opak string, prefix'li (task_, doc_) · filtre/sıralama parametreleri · fields/expand · gzip · CORS · audit log.

Kubernetes: söylenmesi gerekenler

  • Probes: readiness (trafik al), liveness (yeniden başlat; DB'yi kontrol etme!), startup.
  • HPA CPU/RPS'e göre; KEDA kuyruk backlog'una göre. requests/limits, PDB, topology spread (zone).
  • Graceful shutdown: SIGTERM → readiness false → preStop sleep → in-flight bitir → terminationGracePeriodSeconds. SSE/uzun bağlantılar için kritik.
  • Rollout: rolling + maxUnavailable 0; riskli değişiklikte canary (Argo Rollouts, metrik bazlı otomatik rollback). Feature flag ile deploy ≠ release.
  • NetworkPolicy, namespace per servis/takım, ResourceQuota.

Terraform / IaC

  • Modüller (gke-cluster, cloudsql, pubsub-topic+dlq), ortam başına state (GCS backend + lock).
  • PR'da terraform plan yorumu, apply sadece CI'dan (Atlantis / GH Actions + OIDC → Workload Identity Federation, statik key yok).
  • Drift tespiti, policy-as-code (OPA/Conftest). App config: Helm + ArgoCD (GitOps).

Postgres: production ipuçları

  • Connection pool (PgBouncer, transaction mode); pod sayısı × pool < max_connections.
  • EXPLAIN (ANALYZE, BUFFERS), pg_stat_statements, eksik index, N+1.
  • Büyük tablolar: partitioning (zaman / tenant hash), autovacuum ayarı, bloat.
  • Online migration: expand → backfill (batch) → contract. CREATE INDEX CONCURRENTLY. Kilitlenen ALTER'a dikkat, lock_timeout.
  • İş kuyruğu: SELECT … FOR UPDATE SKIP LOCKED (pending_events / job tablosu).
  • Transactional outbox (pending_events tablosu): DB yazımı + event aynı transaction'da → event publisher Pub/Sub'a basar. "DB'ye yazdım ama event kayboldu" problemi yok.
  • Multi-tenant: tenant_id her tabloda, composite index'te ilk kolon, RLS.

Redis kalıpları

  • Cache-aside + TTL jitter + singleflight (stampede). Negative cache.
  • Rate limit: token bucket Lua script (atomik). Idempotency: SET key val NX EX 86400.
  • Distributed lock: kısa TTL + fencing token (Redlock'a güvenme, kritik iş DB'de).
  • Streams: XADD/XREAD BLOCK → canlı event fan-out, consumer group.
  • Eviction policy, memory alarmı, hot key, persistence kapalı mı açık mı?

Güvenilirlik araç kutusu

  • Timeout her dış çağrıda (deadline propagation). Retry sadece idempotent işte, exp. backoff + jitter, retry budget.
  • Circuit breaker (LLM sağlayıcı, kaynak API'ler), bulkhead (tenant/bağımlılık başına havuz).
  • Load shedding: önemsiz işi düşür, önemliyi koru. Kuyrukta öncelik şeritleri.
  • DLQ + alarm + replay aracı. Poison message izolasyonu.
  • Degrade: LLM yoksa arama sonuçları yine dönsün; fallback model.

SRE dili

  • SLI (ölçülen) → SLO (hedef, ör. 99.9% / 30 gün = ~43 dk hata bütçesi) → error budget politikası (bütçe bitti → feature freeze, güvenilirlik işi).
  • Alarm semptoma göre (burn rate, multi-window: 1h & 6h), sebebe göre değil. Her alarmın runbook'u var.
  • RED (Rate, Errors, Duration) servisler için; USE (Utilization, Saturation, Errors) kaynaklar için.
  • Incident: tespit → IC atanır → mitigate (rollback önce!) → iletişim → blameless postmortem → action item.
  • OTel trace: tenant_id, task_id span attribute. Log'da PII yok.

Senaryo A · Mimari ve derin dalışlar7 / 15 · A 3/3

Akışlar

Sync: API → sync_runs INSERT + pending_events (aynı txn) → event publisher → sync-jobs → Crawler: kaynaktan sayfa sayfa değişiklik listesi (delta token), her sayfadan sonra cursor checkpoint (crash olursa kaldığı yerden) → her değişiklik doc-changes (ordering key = document_id) → Processor.

Processor: içeriği çek → content_hash aynı mı? Aynıysa embedding yok, sadece metadata/ACL güncelle → farklıysa chunk + batch embed → tek transaction'da eski chunk'ları sil + yenileri yaz + documents upsert WHERE excluded.source_version > source_version.

Webhook: imza doğrula, 204 dön, sadece "bu doküman değişti" bilgisini kuyruğa at (payload'a güvenme, kaynaktan tekrar çek).

İzin iptali / silme: ayrı yüksek öncelikli topic + worker. Re-embed yok, sadece document_acl / deleted_at. Arama hemen etkilenir.

Derin dalış 1 · İzin doğruluğu (en önemli)

  • Arama: kullanıcının principal kümesi = user_id + grupları (IdP / kaynaktan, Redis'te 5 dk cache). Sorgu önce ACL ile filtreler, sonra vektör benzerliği (pre-filter). Post-filter → top_k boş kalabilir ve sızıntı riski.
  • Fail-closed: ACL bilinmiyorsa dokümanı gösterme. Grup servisi çökerse: son bilinen cache, o da yoksa hata.
  • Periyodik reconciliation job: kaynaktaki ACL ile karşılaştır (webhook'lar kaçabilir).
  • Tenant izolasyonu: RLS + her sorguda tenant_id + entegrasyon testi "tenant A token'ı ile B'nin dokümanı 404".

Derin dalış 2 · Kaynak kotaları ve backoff

  • Redis token bucket: (tenant, source) başına; kaynağın kotasına göre ayarlı. 429 → Retry-After'a uy, run'ı "throttled" işaretle, mesajı gecikmeli tekrar kuyruğa koy (worker'ı uyutma).
  • Kaynak başına circuit breaker: Confluence çökerse Drive senkronu etkilenmez (bulkhead).
  • OAuth token süresi dolarsa: refresh; refresh başarısızsa source auth_error, admin'e bildirim, run'lar durur.

Derin dalış 3 · Noisy neighbor (hot tenant)

  • Spam Lookup tasarımındaki "hot number"ın karşılığı. Büyük tenant onboard olurken 5M doküman kuyruğu doldurur.
  • Çözüm: iki şerit: backfill (ilk sync) ve live (artımlı + ACL). Tenant başına eşzamanlılık limiti (ör. max 20 worker slot). Fair scheduling: job tablosundan round-robin tenant seçimi (FOR UPDATE SKIP LOCKED).
  • Embedding: backfill için spot node pool + batch API (daha ucuz), live için düşük gecikmeli yol.

Hata senaryoları

Worker crashPub/Sub ack gelmez → tekrar teslim. Upsert idempotent (deterministik PK).
Bozuk dosya (poison)N deneme → DLQ, doküman failed, run devam eder.
Postgres failover~30-60 sn yazma hatası → worker'lar retry, API 503 + Retry-After. Arama read replica'dan devam.
Embedding sağlayıcı çöktüCircuit breaker, kuyruk birikir (tazelik SLO'su yanar, veri kaybı yok), alarm.
Kötü deployCanary + otomatik rollback; GCS'te ham içerik → yeniden işleme (replay).

Senaryo B · Mimari ve derin dalışlar10 / 15 · B 3/3

1 · Stream ve devam etme

  • Worker her olayı XADD task:{id}:events ile yazar (artan seq). API pod'u sadece okur → hangi pod'a bağlandığın önemsiz.
  • Kopma: istemci Last-Event-ID ile tekrar bağlanır → XRANGE ile kaçırdıkları + XREAD BLOCK ile canlı.
  • Redis stream'i 24 saat sonra silinir; kalıcı kayıt Postgres'te (final mesaj, tool çağrıları).
  • Deploy: API pod'u SIGTERM alınca yeni bağlantı kabul etmez, mevcut stream'lere retry: 1000 gönderip kapatır → istemci başka pod'a devam eder. LB idle timeout > keep-alive aralığı.

2 · Dayanıklı yürütme (worker crash)

  • Worker task'ı lease ile alır (lease_until, heartbeat 10 sn). Lease biterse başka worker devralır.
  • Her adımdan sonra checkpoint (mesaj geçmişi + tamamlanan tool sonuçları). Devralan worker oradan devam eder, baştan değil.
  • Çok uzun/karmaşık iş akışları büyürse: Temporal gibi workflow motoru. Trade-off: yeni bir sistem işletmek.

3 · Tool yan etkileri: en fazla bir kez

  • Yazan tool'larda side_effect_key = task_id + tool_call_id → hedef API'ye idempotency key olarak geçir veya önce DB'ye "started" yaz, sonuç gelince "done".
  • Crash sonrası "started" ama "done" yok → hedefte kontrol et (ör. bu key ile ticket var mı?) veya kullanıcıya sor. Körlemesine tekrar etme.

4 · LLM Gateway ve kotalar

  • Tenant başına token bucket (dakikalık hız + günlük bütçe), Redis Lua. Çağrı öncesi tahmini token rezerve, sonra gerçek kullanımla düzelt.
  • Sağlayıcı 429/5xx: exp. backoff, sonra fallback model/sağlayıcı; circuit breaker. Timeout: ilk token için 10 sn, toplam için 120 sn.
  • Öncelik: interaktif (web) > async (API) > batch. Yük altında batch'i kuyrukta beklet.
  • Kullanım ve maliyet olayları → faturalama ve tenant dashboard'u.

5 · Güvenlik ve multi-tenancy

  • Tool'lar kullanıcının OAuth token'ı ile çalışır (kullanıcının göremediğini agent de göremez).
  • Prompt injection: tool çıktısı = güvenilmeyen veri; yazan tool'lar için insan onayı (requires_action), en az yetki scope'u.
  • Task'lar ve olaylar tenant_id ile; Redis key'lerinde de tenant prefix.

package main
import (...) // context, crypto/sha256, encoding/hex,
  // encoding/json, errors, log/slog, net/http, time

type SyncRun struct {
  ID          string    `json:"id"`
  TenantID    string    `json:"-"`
  SourceID    string    `json:"source_id"`
  Mode        string    `json:"mode"`
  Status      string    `json:"status"`
  CreatedAt   time.Time `json:"created_at"`
}

// one error shape for the whole API
type APIError struct {
  Status int    `json:"status"`
  Code   string `json:"code"`
  Title  string `json:"title"`
}

func (e *APIError) Error() string { return e.Code }

// in-memory fake in tests, Postgres in prod
type Store interface {
  SourceExists(tenant, source string) bool
  ByIdempotencyKey(tenant, key string) (SyncRun, string, bool)
  ActiveRun(tenant, source string) (SyncRun, bool)
  // prod: UNIQUE(tenant_id, key) + pending_events row, one txn
  Create(run SyncRun, key, bodyHash string) error
}

type Server struct {
  store Store
  newID func() string
  now   func() time.Time
}

func (s *Server) Routes() *http.ServeMux {
  mux := http.NewServeMux() // Go 1.22 patterns
  mux.HandleFunc("POST /v1/sources/{id}/syncs", s.handle(s.createSync))
  return mux
}

type handlerFunc func(w http.ResponseWriter, r *http.Request) error

func (s *Server) handle(h handlerFunc) http.HandlerFunc {
  return func(w http.ResponseWriter, r *http.Request) {
    if err := h(w, r); err != nil {
      var ae *APIError
      if !errors.As(err, &ae) {
        slog.Error("unhandled", "err", err,
          "request_id", r.Header.Get("X-Request-Id"))
        ae = &APIError{500, "INTERNAL", "unexpected error"}
      }
      writeJSON(w, ae.Status, ae, "application/problem+json")
    }
  }
}
func (s *Server) createSync(w http.ResponseWriter, r *http.Request) error {
  // set by auth middleware from the verified JWT
  tenant := TenantFrom(r.Context())
  source := r.PathValue("id")
  key := r.Header.Get("Idempotency-Key")
  if key == "" {
    return &APIError{400, "IDEMPOTENCY_KEY_REQUIRED", "missing key"}
  }
  var body struct {
    Mode string `json:"mode"`
  }
  r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
  if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
    return &APIError{400, "INVALID_JSON", "bad json"}
  }
  if body.Mode == "" {
    body.Mode = "incremental"
  }
  if body.Mode != "full" && body.Mode != "incremental" {
    return &APIError{400, "INVALID_MODE", "full|incremental"}
  }
  if !s.store.SourceExists(tenant, source) {
    // same 404 for another tenant's id: no leak
    return &APIError{404, "NOT_FOUND", "source not found"}
  }
  sum := sha256.Sum256([]byte(body.Mode))
  hash := hex.EncodeToString(sum[:])

  if prev, h, ok := s.store.ByIdempotencyKey(tenant, key); ok {
    if h != hash {
      return &APIError{409, "IDEMPOTENCY_KEY_REUSED", "body differs"}
    }
    w.Header().Set("Location", "/v1/syncs/"+prev.ID)
    writeJSON(w, 202, prev, "") // replay first answer
    return nil
  }
  if active, ok := s.store.ActiveRun(tenant, source); ok {
    w.Header().Set("Location", "/v1/syncs/"+active.ID)
    writeJSON(w, 200, active, "") // documented choice
    return nil
  }
  run := SyncRun{ID: "syn_" + s.newID(), TenantID: tenant,
    SourceID: source, Mode: body.Mode,
    Status: "queued", CreatedAt: s.now().UTC()}
  if err := s.store.Create(run, key, hash); err != nil {
    return err // real store: unique violation → replay/409
  }
  w.Header().Set("Location", "/v1/syncs/"+run.ID)
  writeJSON(w, 202, run, "")
  return nil
}

Neden Ory? (alternatifler)

Entra + custom UserInfoEn basit, ama her istekte ekstra çağrı ve gecikme; sadece Entra; offline yok.
Entra custom claimsDeğişiklik için Global Admin; düz claim yapısı, JSON yok; loglar ekipte değil.
KeycloakKullanıcıların ayrı kopyası + senkronizasyon; özelleştirme Java'da; dik öğrenme eğrisi.
Ory ✓Standart OIDC/OAuth2, en esnek token hook, çoklu IdP, olası offline, iyi admin araçları. Bedeli: self-hosted.

Hazır cevaplar (İngilizce)

Why Ory? We needed standard OIDC so any team could use off-the-shelf libraries, a token hook to add our permission claims, and room for more than one identity provider. Entra alone meant an extra user-info call per request, or admin-only custom claims with a flat structure. Keycloak meant syncing a copy of all users and writing Java plugins. Ory gave us all of it; the price was running it ourselves.

Biggest trade-off? Putting authorization data in the token made checks local and fast, but revocation was slower and the token kept growing. Later the team hit a size ceiling for users with many markets and moved fine-grained authorization to a central, cached decision service.

How did you make adoption easy? We wrapped verification in small libraries, so teams called verify or getContexts and never parsed tokens themselves. That also let us change the backend later without breaking anyone.

Security team? After it was live, the central security team wanted visibility in Entra. We kept the token format and libraries and switched to standard OAuth token exchange, so consumers barely noticed.

Do differently? (önerilen yansıma, katılıyorsan kullan) I'd keep authentication in the token but plan for fine-grained authorization as a cached decision API earlier, because the token-size limit was predictable.

AI Company'ye köprü: Senaryo A'daki izin farkındalıklı arama aynı soru: izinler token'da mı, indekste mi, merkezi bir kontrolde mi? Bu sayfadaki trade-off'ları orada kullan.
