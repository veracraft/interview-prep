Deployment API · 4. Hata ve güvenlik

Playbook 4/5 · Hata ve güvenlik. Ne yaparsın: retry, eşzamanlılık, çökme, yetki, silme. Her cevap: karar → gerekçe → bedel. Gösterdiğin: sistemin güvenilir olduğunu.

Karar soruları

Her cevap: karar → gerekçe → bedel veya alternatif. Aynı sorular diğer iki sistemde de var; cevapları farklı.

SoruKararGerekçeBedel / alternatif
What must be saved before returning 202?deployments satırı ('pending', idempotency key ile) commit edilir. Ayrı bir pending_events gerekmez: kuyruk Postgres'in kendisi, satır yazıldığı an iş kuyruktadır.202 "deploy kaybolmayacak" sözüdür.DB yoksa 503 + Retry-After; CI tekrar dener.
What happens when CI retries?UNIQUE (service_id, idempotency_key) → aynı deployment döner.CI job'ları yeniden denenir; iki deploy başlamamalı.CI key üretmeli (ör. pipeline run id). Key yoksa sadece "tek aktif deploy" korur.
What if two deploys target the same service and environment?Partial unique index (servis + ortam + aktif durum); ikincisi 409 DEPLOYMENT_IN_PROGRESS + çalışan deploy'un id'si.İki rollout aynı anda birbirini ezer.CI beklemeli ya da iptal etmeli. Alternatif: servis başına sıra (daha karmaşık).
Who may deploy or approve?CI'ın OIDC kimliği (repo) bir takıma eşlenir; takım servisin sahibi olmalı. Sadece imzalı image; cluster da admission policy ile tekrar kontrol eder. Prod'u ikinci bir kişi onaylar; kendi deploy'unu onaylayamazsın.Prod'a rastgele bir image gitmemeli; tek kişi hatası engellenmeli.Onay deploy'u yavaşlatır; acil durum için audit'li break-glass yolu gerekir.
How does CI see progress or failure?GET /v1/deployments/{id} ile backoff'lu polling: durum, canary adımı, commit; başarısızlıkta neden kodu. Worker bunları Argo CD'den okuyup yazar. 4. aşamada Slack ve webhook.Basit, her proxy'den geçer; CI için canlı akışa gerek yok.Polling yükü küçük (günde birkaç yüz deploy).
What do cancel and rollback do mid-rollout?:cancel: worker Argo Rollouts'a rollout'u iptal ettirir (abort), trafik eski sürüme döner, sonra config reposunu eski digest'e geri alır. :rollback: önceki sağlıklı digest'i commit'leyen yeni bir deployment.Geri dönüş de bir commit; geçmiş Git'te ve deployments'ta tek çizgide.Rollback da birkaç dakika sürer (Argo CD sync + Rollouts).
What if the worker crashes mid-rollout?Rollout durmaz: Argo CD ve Rollouts worker'dan bağımsız çalışır. Lease biter, başka worker devralır; commit zaten repodaysa tekrar atmaz, izlemeye devam eder.Yürütme ile takip ayrı; worker'ın ölmesi deploy'u etkilememeli.Worker yokken Postgres'teki durum birkaç saniye geride kalır.
What if the Deploy API is down during an incident?Çalışan servisler ve süren rollout'lar etkilenmez: API müşteri trafiğinin yolunda değil, yürütme Argo CD'de. Acil rollback için ekip config reposundaki commit'i doğrudan geri alır (break-glass); Git geçmişi audit kaydı.Deploy platformu, kendi arızasında insanları kilitlememeli.API'yi atlayan değişiklik politikayı da atlar; sonradan API'ye kaydedilmeli.
Someone changes the cluster by hand with kubectl.Argo CD farkı (drift) görür ve repodaki hale geri döndürür (self-heal). Kalıcı değişiklik sadece Git'ten.Git tek doğruluk kaynağı olmalı; yoksa ne çalıştığını kimse bilmez.Acil elle düzeltme de geri alınır; o yüzden acil durum yolu Git'ten (revert).
How do we know it's healthy?Deploy başarı oranı, süresi (p95), rollback oranı, takım başına merge'den prod'a süre; API için hata oranı ve gecikme.Platform ekibinin gerçek ölçüsü: geliştiriciler ne kadar hızlı ve güvenle çıkıyor.Metrikleri takım bazında göstermek; kardinalite küçük, sorun değil.
