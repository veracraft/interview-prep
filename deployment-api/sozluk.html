Gateway #

Aşama 1
Ne?
API'lerin önündeki güvenlik görevlisi. Her isteği API'ye ulaşmadan kontrol eder.
Benzetme
Binanın girişindeki turnike ve güvenlik.
Bizde
CI'ın OIDC token'ını (repo ve takım kimliği, kısa ömürlü, secret yok) ya da geliştiricinin SSO token'ını doğrular; rate limit uygular.
Hangi problemi çözüyor? Kimlik doğrulama, rate limit ve istek boyutu sınırı tek yerde.
Neden şimdi? 1. aşama: güvenlik sonraya bırakılmaz.
Daha basit alternatif: Her serviste aynı middleware (az servis varken yeter).
Bedeli: Bir ağ adımı daha; yanlış ayar tüm trafiği etkiler.
The gateway handles cross-cutting concerns once: token validation, rate limits, request size. So every service doesn't reimplement them.

API (Deploy API) #

Aşama 1
Ne?
Dış dünyanın sistemle konuştuğu kapı. HTTP istekleri alır, kontrol eder ve cevap döner.
Benzetme
Restorandaki garson. Siparişi alır, deftere yazar, "tamam, hazırlanıyor" der. Yemeği kendisi pişirmez.
Bizde
Deploy API. Takımın servisin sahibi olduğunu ve aktif deploy olmadığını kontrol eder, deployments satırını yazar, 202 döner. Rollout'u kendisi yapmaz.
Stateless
API kendi içinde bir şey hatırlamaz, her şey Postgres'te. Bu yüzden 1 pod da çalışabilir, 20 pod da; Kubernetes yük artınca pod ekler (HPA).
Hangi problemi çözüyor? İstemciye net bir sözleşme; isteği doğrulayıp kalıcı kaydetmek.
Neden şimdi? 1. aşama: o olmadan sistem yok.
Daha basit alternatif: Yok; istemcinin doğrudan veritabanına yazması kabul edilemez.
Bedeli: Ağır işi içinde yaparsa timeout; stateless tutulmalı.
The API layer is stateless. It validates the request, records it durably, and returns 202. The heavy work happens in workers.

202 Accepted ve uzun süren iş #

Aşama 1
Ne?
"İsteğini aldım ve kaydettim, ama iş henüz bitmedi" demek. Cevapta işin durumunu sorgulayabileceğin bir adres döner (Location header'ı).
Benzetme
Kuru temizlemecinin fişi. Elbiseyi bıraktın, fişi aldın; ne zaman hazır olduğunu fişle sorarsın.
Bizde
Rollout dakikalar sürer. CI GET /v1/deployments/{id} ile durumu sorar.
Dikkat
202 dönmeden önce iş kalıcı olarak kaydedilmiş olmalı. Kaydetmediğin işi kabul etme.
This operation can take minutes, so instead of holding the request open I return 202 with a status resource the client can poll.

Idempotency #

Aşama 1
Ne?
Aynı isteği bir kez de yapsan, beş kez de yapsan sonuç aynı kalır.
Benzetme
Asansör düğmesi. Beş kez bassan da asansör bir kez gelir.
Bizde
CI tekrar gönderirse Idempotency-Key aynı deployment'ı döner. Worker'ın commit'i de tekrarlanabilir: repo zaten o digest'teyse yeni commit atılmaz. Detay →
Gerçek hayattan
Ödeme sistemlerinde aynı işlem iki farklı yoldan tetiklenirse iki müşteri kaydı ya da iki fatura oluşabilir. Çözüm önce tasarımda: her yan etkinin tek bir sahibi olsun; idempotency key bunun üstüne güvenlik ağı.
Clients will retry, so every mutating call accepts an Idempotency-Key. And each side effect has exactly one owner, with the key as a safety net.

Image digest #

Aşama 1
Ne?
Container image'ının içeriğinden hesaplanan değişmez kimlik: …@sha256:9f2…. Tag (:v1.4, :latest) başka bir image'a taşınabilir; digest taşınamaz.
Bizde
API sadece digest kabul eder; tag gelirse 400. Rollback önceki sağlıklı deployment'ın digest'ine döner.
Hangi problemi çözüyor? Ne deploy edildiğinden emin olamamak.
Neden şimdi? 1. aşama: API sözleşmesinin parçası.
Daha basit alternatif: Tag kabul etmek.
Bedeli: CI digest'i iletmeli; insanlar için okunması zor (yanında tag'i de gösteririz).
I deploy by image digest, not tag, so we always know exactly what runs and a rollback goes back to the exact previous version.

Postgres #

Aşama 1, 2
Ne?
Ana veritabanı. Kalıcı ve doğru olması gereken her şey burada.
Bizde
services, deployments. Aynı zamanda kuyruk: worker bekleyen deploy'u FOR UPDATE SKIP LOCKED ile alır. Örnek satırlar →
Neden
Transaction ve unique constraint ile doğruluğu garanti eder. Başka bir veritabanını (ör. Cassandra) ancak gerçek bir yazma sınırına ulaşınca önerirsin.
Multi-tenant
Her tabloda tenant_id; bir müşteri asla başka müşterinin verisini görmemeli. Katmanlar →
Hangi problemi çözüyor? Kalıcı ve doğru durum; unique ve transaction ile kuralları veritabanı garanti eder.
Neden şimdi? 1. aşama; 2. aşamada kuyruk olarak da.
Daha basit alternatif: Bu zaten en basit seçenek; günde birkaç yüz iş için ayrı kuyruk gerekmez.
Bedeli: Tek yazma noktası; büyüyünce read replica ve partition.
Postgres is the source of truth. Uniqueness and state transitions are enforced there, not just in application code.

Deploy worker #

Aşama 2
Ne?
Deploy'u başlatıp izleyen arka plan süreci. Rollout'u kendisi yapmaz.
Ne yapar
  1. Bekleyen deploy'u Postgres'ten FOR UPDATE SKIP LOCKED ile alır ve lease yazar.
  2. Prod ise onay bekler.
  3. Config reposuna yeni image digest'i ile commit atar.
  4. Argo CD'den sync, health ve canary adımını izler; Postgres'e yazar.
Çökerse
Rollout durmaz: Argo CD ve Rollouts kendi başına devam eder. Lease biter, başka worker devralır; commit zaten repodaysa tekrar atmaz, izlemeye devam eder.
Hangi problemi çözüyor? Deploy'u API isteğinin dışında başlatıp sonucunu takip etmek.
Neden şimdi? 2. aşama.
Daha basit alternatif: API isteğinin içinde commit atmak (izleme yine bir yere lazım).
Bedeli: Git ile Postgres arasında iki durum: commit atıldı ama kaydedilemediyse, worker repoya bakıp düzeltir.
The worker just claims the deployment, commits the new digest to the config repo and watches Argo CD. If it dies, the rollout keeps going, and another worker picks up the watching.

GitOps ve config reposu #

Aşama 2
Ne?
Cluster'da ne çalışması gerektiğini bir Git reposunda tutmak. Değişiklik = commit. Bir araç (Argo CD) cluster'ı sürekli repodaki duruma getirir.
Bizde
apps/checkout/prod/values.yaml içindeki image digest'i. Worker bunu değiştiren commit'i atar; commit mesajında deployment id'si var.
Neden
Git tek doğruluk kaynağı: ne çalıştığı, ne zaman ve kim tarafından değiştirildiği Git geçmişinde. Geri almak = commit'i geri almak.
IaC ile farkı
Terraform altyapıyı kurar (cluster, Argo CD'nin kendisi, registry). GitOps uygulamaların hangi sürümde çalışacağını yönetir. İkisi farklı katman.
Hangi problemi çözüyor? Cluster'daki durumun nereden geldiğini bilmemek; elle yapılan değişiklikler.
Neden şimdi? 2. aşama: ekip zaten Argo CD kullanıyor.
Daha basit alternatif: Worker'ın Kubernetes API'sine doğrudan apply etmesi.
Bedeli: Git'e yazma hızı ve çakışmalar; aynı dosyaya iki commit (tek aktif deploy kuralı bunu önler).
Git is the source of truth for what runs. A deploy is just a commit that changes the image digest, and Argo CD makes the clusters match it.

Argo CD #

Aşama 2
Ne?
Kubernetes içinde çalışan bir GitOps aracı. Repoyu izler ve cluster'ı oradaki duruma getirir (sync).
Self-heal
Biri cluster'da elle bir şey değiştirirse Argo CD farkı (drift) görür ve repodaki hale geri döndürür.
Bizde
Her servis + ortam bir Argo CD uygulaması (ör. checkout-prod). Worker onun sync ve health durumunu okur. Çok cluster'da ApplicationSet ile her cluster'a aynı uygulama.
Hangi problemi çözüyor? Repodaki durumu cluster'lara güvenle ve sürekli uygulamak.
Neden şimdi? 2. aşama.
Daha basit alternatif: Worker'ın kendi apply döngüsü.
Bedeli: Argo CD'yi işletmek; çok sayıda uygulamada performans ayarı (sharding).
Argo CD watches the config repo and keeps every cluster in sync with it, including undoing manual changes.

Kubernetes #

Aşama 2
Ne?
Container'ları çalıştıran platform. "İstenen durumu" yazarsın (bu image, bu kadar pod); Kubernetes oraya kendisi ulaşır.
Bizde
Kimse doğrudan dokunmaz; Argo CD uygular. 3. aşamada servis Deployment yerine Argo Rollouts kaynağı olarak tanımlıdır.
Nobody applies to the cluster by hand; Argo CD does, from Git.

Canary ve Argo Rollouts #

Aşama 3
Ne?
Yeni sürümü önce trafiğin küçük bir kısmına açmak (%10), sağlıklıysa adım adım artırmak (%50, %100).
Benzetme
Madencilerin kanaryası: tehlikeyi herkesten önce küçük bir grup fark eder.
Argo Rollouts
Bunu yapan Kubernetes eklentisi. Adımlar ve analiz Rollout kaynağında tanımlı: her adımdan sonra Prometheus'a sorar; kötüyse kendini iptal eder ve trafiği eski sürüme döndürür. Canary mantığını biz yazmıyoruz.
Hangi problemi çözüyor? Kötü bir sürümün tüm kullanıcıları etkilemesi.
Neden şimdi? 3. aşama: otomatik rollback istendi.
Daha basit alternatif: Düz rolling update + insanın izlemesi.
Bedeli: Daha uzun deploy; trafik bölme ve iyi metrikler gerekir.
Argo Rollouts does the canary: it shifts traffic in steps, runs an analysis against Prometheus after each step, and aborts back to the stable version if it fails.

Prometheus #

Aşama 3
Ne?
Metrik sistemi: hata oranı, gecikme, istek sayısı.
Bizde
Argo Rollouts'un analiz adımı sorgular: yeni pod'ların 5xx oranı ve p99'u, aynı anda çalışan eski pod'larla karşılaştırılır. Yeterli trafik yoksa karar verilmez.
Hangi problemi çözüyor? Rollout'un sağlıklı olup olmadığını otomatik bilmek.
Neden şimdi? 3. aşama.
Daha basit alternatif: İnsan izler, elle rollback yapar.
Bedeli: Az trafikte karar verilemez; metrik sorguları iyi yazılmalı.
The analysis compares the canary with the stable pods at the same time, so a busy hour doesn't look like a bad release.

Prod onayı #

Aşama 4
Ne?
Prod deploy'unun ikinci bir kişi tarafından onaylanması (four-eyes).
Bizde
Deploy commit'ten önce awaiting_approval durumunda bekler; POST /v1/deployments/{id}:approve. Kendi deploy'unu onaylayamazsın (403). Her şey audit log'da.
Alternatif
Worker commit yerine config reposunda PR açar; onay = PR review (CODEOWNERS). Git'e yakın ama durum API'de ve PR'da ikiye bölünür.
Hangi problemi çözüyor? Tek kişinin hatalı ya da kötü niyetli prod deploy'u.
Neden şimdi? Follow-up (4. aşama): prod politikası gerektiriyorsa.
Daha basit alternatif: Sadece imzalı image ve servis sahipliği.
Bedeli: Deploy süresi uzar; acil durumda audit'li bir break-glass yolu gerekir.
Production deploys wait for a second person to approve, and you can't approve your own.

Notifier #

Aşama 4
Ne?
Sonucu (bitti, rollback oldu, onay bekliyor) Slack'e ve kayıtlı webhook'lara gönderen bileşen.
Hangi problemi çözüyor? Ekiplerin sonucu polling yapmadan öğrenmesi.
Neden şimdi? 4. aşama.
Daha basit alternatif: Sadece GET ile polling.
Bedeli: Webhook teslimi: retry, imza, kaybolan bildirim.
Teams get pushed a notification when a deploy finishes or needs approval, so they don't have to watch it.
