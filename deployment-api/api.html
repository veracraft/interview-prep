Deployment API · 2. API sözleşmesi

Playbook 2/5 · API sözleşmesi. Ne yaparsın: endpoint'ler → bir tam request/response → durumlar → hatalar. Idempotency ve yetkiyi burada söyle. Gösterdiğin: istemcinin servisi nasıl kullanacağını.

Önce kağıda kendin yaz, sonra butonla karşılaştır.

Endpoint'e ya da hata koduna tıkla: altında istek ve cevap açılır. ↗ işaretli hücreye tıkla: ilgili karar açılır.

Kaynaklar: service (sahibi bir takım) · deployment (uzun süren iş) · environment (staging, prod)

Akış: CI gönderir → API sahipliği ve aktif deploy'u kontrol edip kaydeder → 202 döner → CI Location'ı sorar. Aşağıda aynı istek satır satır.

İstekNe demek, neden?
POST /v1/services/checkout/deploymentscheckout servisi için yeni bir deploy başlat. Deploy servisin altında yaşar; tek aktif deploy kuralı servis + ortam başına.
Authorization: Bearer <CI OIDC token>Kim olduğun: CI'ın kendi kısa ömürlü kimliği (hangi repo). Uzun ömürlü bir secret yok. API bu repoyu bir takıma eşler ve servisin sahibi mi diye bakar. Token'dan nasıl? →
Idempotency-Key: 7c9e…CI job'u yeniden denenirse aynı anahtarla gelir; ikinci deploy başlamaz, aynı deployment döner. Pratikte pipeline run id.
"environment": "prod"Nereye: staging ya da prod. Prod'da onay ve daha sıkı kurallar.
"image": "…@sha256:9f2…"Ne: image'ın digest'i, tag değil. Digest değişmez; tam olarak neyin çalıştığını bilirsin.
"strategy": { "type": "canary", "steps": [10, 50, 100] }Nasıl: önce trafiğin %10'u, sağlıklıysa %50, sonra %100. Bunu Argo Rollouts uygular; API sadece adımları seçtirir.
CevapNe demek, neden?
202 Accepted"Aldım ve kaydettim; rollout arka planda." Rollout dakikalar sürer.
Location: /v1/deployments/dep_481Durumu nereden soracağın. CI bu adrese backoff'lu GET atar.
{ "id": "dep_481", "status": "pending" }Deploy'un kimliği ve ilk durumu.
pending → progressing → (awaiting_approval) → succeeded
                      ↘ failed | rolled_back | cancelled

Kural / kararNeden?
Image digest, tag değilTag değişebilir, digest değişmez; rollback tam olarak eski sürüme döner.
Servis + ortam başına tek aktif deployİki rollout aynı anda birbirini ezer; partial unique index garanti eder.
Tekrar: aynı Idempotency-Key → aynı deployCI job'ları yeniden denenir.
Rollback yeni bir deploymentGeçmiş tek bir çizgi kalır: ne zaman, hangi digest, kim.
Yürütme GitOps'taAPI Kubernetes'e dokunmaz; config reposuna commit atar, Argo CD uygular, Argo Rollouts canary'yi yapar.
REST, gRPC değilCI ve CLI'dan kolay çağrılır, gateway'den geçer, insan okuyabilir; yüksek hacimli servisler arası trafik yok.
I deploy by image digest, not tag, so we always know exactly what runs and a rollback goes back to the exact previous version.
