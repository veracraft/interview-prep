Tek aktif deploy kuralı: UNIQUE (service_id, environment) WHERE status IN ('pending','progressing','awaiting_approval'). Bu kural config reposunda aynı dosyaya iki commit'in yarışmasını da önler.

Kafka ve Redis neden yok? Günde birkaç yüz deploy var; Postgres hem kayıt hem kuyruk olabilir. Asıl yürütme Argo CD ve Argo Rollouts'ta; bizim worker sadece commit atar ve izler. Her kutunun bir nedeni olmalı; nedeni yoksa çizme.

Aşamaların yazılı özeti
  1. 1 · Temel istek. CI image'ı build edip imzaladıktan sonra deploy'u başlatır (ok 1). Gateway CI'ın OIDC token'ını doğrular (ok 2). Deploy API takımın servisin sahibi olduğunu, image'ın imzalı olduğunu ve aynı servis + ortamda aktif deploy olmadığını kontrol eder, Postgres'e 'pending' satırı yazar (ok 3) ve 202 döner. CI GET /v1/deployments/{id} ile durumu sorar.
  2. 2 · GitOps ile rollout. Deploy worker bekleyen deploy'u Postgres'ten alır (ok 4). Kubernetes'e kendisi dokunmaz: config reposunda image digest'ini değiştiren bir commit atar (ok 6). Argo CD commit'i görür (ok 7) ve cluster'ları bu duruma getirir (ok 8). Worker Argo CD'den durumu izler (ok 9) ve Postgres'e yazar (ok 5). Git tek doğruluk kaynağı: cluster'da ne çalıştığı her zaman repodan okunur.
  3. 3 · Canary ve otomatik rollback. Kubernetes'te Deployment yerine Argo Rollouts kaynağı: %10 → analiz → %50 → analiz → %100. Her analizde Prometheus'a sorulur (ok 10). Kötüyse rollout kendini iptal eder ve trafik eski sürüme döner; worker bunu izlerken görür (ok 9) ve deploy'u rolled_back yapar. Canary mantığını biz yazmıyoruz.

Neden API, GitOps varken?

Takımlar config reposuna doğrudan PR açıp merge edebilirdi. API'yi onun yerine değil, önüne koyuyoruz.

KararDeploy API politika ve sözleşme katmanı; yürütme GitOps'ta (Argo CD, Argo Rollouts). API Kubernetes'e hiç dokunmaz, sadece config reposuna commit atar.
Gerekçe
  • Politika tek yerde: takım servisin sahibi mi, image imzalı mı, prod onayı alındı mı. Git'te bunlar dağınık kurallarla (CODEOWNERS, branch protection) çözülür.
  • Tek giriş, tek durum: CI, CLI ve Slack aynı endpoint'i çağırır; "bu deploy hangi adımda, kim başlattı" tek bir GET ile görülür. Git'te bunun için commit, Argo CD ve Rollouts ayrı ayrı okunmalı.
  • Sözleşme sabit: arkadaki araç değişse (Argo CD yerine başka bir şey) istemciler değişmez.
  • Tekerleği yeniden icat etmiyoruz: sync, drift düzeltme ve canary hazır araçlarda.
Bedel / alternatifBir servis daha işletmek; Git ile Postgres arasında iki durum (commit atıldı ama kaydedilemedi gibi). Alternatif: sadece PR + CODEOWNERS + Argo CD; küçük ekipte yeterli, ama durum ve politika dağınık kalır.

Altyapının kendisi (cluster'lar, Argo CD'nin kurulumu, registry) Terraform ile kurulur; uygulamaların sürümü Argo CD ile yönetilir. IaC ve GitOps farklı katmanlar.

I'm not rewriting Kubernetes deployment. Argo CD and Argo Rollouts are the execution engine; the Deploy API is the policy and contract layer on top: ownership, signed images, approvals, one status for CI. The worker just commits the new digest to the config repo and watches.
This is the simplest version that works: Postgres is both the record and the queue, and Argo CD does the rollout. Where would you like me to go deeper?
