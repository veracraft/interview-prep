Deployment API · Mock mülakat

Infra rolüne en yakın soru için kısaltılmış bir görüşme. Interviewer doğal İngilizce konuşuyor; aday (sen) basit B2 İngilizcesiyle.

Nasıl çalışılır?
  1. Bir kez baştan sona sesli oku; iki rolü de sen oku.
  2. "Adayın cevaplarını gizle"ye bas. Interviewer'ı oku, cevabı kendi cümlelerinle sesli söyle, sonra gizlemeyi kapatıp karşılaştır.
  3. Telefonla kendini kaydet. Cevaplar 20-40 saniyeyi geçiyorsa kısalt.
Yeşil notlar (▸ Neden işe yarıyor?) Türkçe koçluk notlarıdır.

Infra rolüne en yakın soru: ürün değil, iç platform API'si. Tanışma kısmı Mock A ile aynı. Deployment API sayfası · Diyagram C

03:00 · Problem ve netleştirme
Interviewer
We have about two hundred services, owned by different teams, running on Kubernetes. Today every team deploys in its own way. We want one internal API that teams use to deploy their services, from CI or from a CLI. Design the API and the system behind it.
Sen
Okay. Some questions first. Who calls the API, only CI pipelines or also engineers from laptop? And what do you already use for deploys, something like Argo CD?
Interviewer
Both, but mostly CI. We already run Argo CD with a config repo, and Terraform for the clusters.
Sen
How many clusters and regions? And which strategies you want, only rolling update or also canary?
Interviewer
Three clusters in two regions. Canary would be great, with automatic rollback.
Sen
For production, does someone need to approve? And are the images signed?
Interviewer
Yes to both. Prod needs a second person, and CI signs the images.
Sen
Okay. So it's not big scale, a few hundred deploys per day. The hard parts are correctness, like two deploys at the same time or a rollout that stops in the middle, and security: who can deploy what.
Neden işe yarıyor?Ölçeğin küçük olduğunu söyleyip zorluğu doğruluk ve güvenliğe taşıman, gereksiz Kafka/Cassandra konuşmasını baştan keser ve doğru problemi gördüğünü gösterir.
07:00 · API
Sen
I start with the API. 
POST /v1/services/{service}/deployments   → 202 + Location  (Idempotency-Key)
GET  /v1/deployments/{id}                 → status, current step
GET  /v1/services/{service}/deployments   → history, cursor
POST /v1/deployments/{id}:approve         → prod approval
POST /v1/deployments/{id}:rollback        → 202
POST /v1/deployments/{id}:cancel          → 202
The body has the environment, the image by digest, and the strategy. Status goes pending, progressing, maybe awaiting approval, then succeeded, failed, rolled back or cancelled.
Interviewer
Why the digest and not a tag?
Sen
A tag can move, a digest can not. So we know exactly what is running, and a rollback goes back to exactly the old version.
Interviewer
What happens if CI sends the same request twice, or two people deploy the same service?
Sen
Same request twice: the Idempotency-Key returns the same deployment. Two different deploys for the same service and environment: only one can be active, there is a partial unique index in Postgres, so the second one gets 409 with the id of the running deployment.
Neden işe yarıyor?API kısmında üç şey puan getirir: digest gerekçesi, idempotency ile "tek aktif iş" kuralını ayırman ve 409'da çalışan deploy'un id'sini dönmen (istemci ne yapacağını bilir).
14:00 · Basit v1
Interviewer
Okay, how does it work behind the API?
Sen
Simple version first. CI calls the gateway, the gateway checks the OIDC token, then the Deploy API. The API checks the team owns the service, writes a deployment row with status pending and returns 202. A deploy worker takes pending rows from Postgres with SELECT FOR UPDATE SKIP LOCKED, and commits the new image digest to the config repo. Argo CD syncs it to the clusters, and the worker watches the status and writes the progress back. CI polls the status.
Interviewer
Why not put a queue like Kafka in between?
Sen
We can, but it's a few hundred deploys per day. Postgres can be the queue here, it's one less system to run. If later other systems want to listen to deploy events, I add a pending_events table and a publisher, but not now.
Neden işe yarıyor?Gereksiz parçayı reddetmek kıdem sinyali; "ne zaman eklerdim" koşulunu da söylediğin için inatçı görünmezsin.
Interviewer
You already have Argo CD. Why do we need an API at all? Teams could just open a PR to the config repo.
Sen
For a small team, a PR is enough. But then the rules are in many places: who owns the service, is the image signed, who approved prod. And CI has to read Git, Argo CD and Rollouts to know the status. The API keeps the rules and the status in one place, and it still uses Git and Argo CD underneath. I don't write my own deploy engine.
Neden işe yarıyor?Mülakatçı mevcut araçları savunabilir; sen GitOps'u reddetmiyorsun, üstüne politika ve durum katmanı koyuyorsun. "I don't write my own deploy engine" cümlesi infra rolünde güçlü bir sinyal.
20:00 · Canary ve rollback
Interviewer
How does the canary work, and when do you roll back?
Sen
We use Argo Rollouts for this, I don't write it myself. It goes in steps: ten percent, fifty, then hundred. After each step an analysis checks Prometheus: error rate and p99 of the new pods compared with the old pods. If it is worse, Rollouts aborts and goes back to the old version by itself, and the worker sees it and marks the deployment rolled back.
Interviewer
Why compare with the old pods and not a fixed threshold?
Sen
Because traffic changes during the day. If I compare at the same time, a busy hour doesn't look like a bad deploy.
Neden işe yarıyor?Mutlak eşik yerine eşzamanlı karşılaştırma, gerçek canary deneyimi gibi duyulur.
26:00 · Hata senaryoları
Interviewer
The worker crashes in the middle of a rollout. What happens?
Sen
The rollout doesn't stop, because Argo CD and Rollouts don't need the worker. The worker only commits and watches. It has a lease on the deployment row; when the lease expires, another worker takes it, sees the commit is already in the repo, and just continues watching.
Interviewer
And if the Deploy API itself is down during an incident?
Sen
Running services are not affected, the API is not in the path of customer traffic. Running rollouts also continue, because Argo CD does the work. For an emergency rollback the team can revert the commit in the config repo directly, and the Git history is the audit log. But I run the API in more than one zone, so this should be rare.
Neden işe yarıyor?"API müşteri trafiğinin yolunda değil" cümlesi bu tasarımın en önemli güvenilirlik argümanı. Break-glass'ı audit ile söylemek de olgunluk gösterir.
31:00 · Güvenlik
Interviewer
How do you make sure nobody deploys something random to production?
Sen
Four things. CI has its own identity with OIDC, no long-lived secrets. The API checks the team owns the service. Only signed images, and the cluster checks it again with an admission policy. And production needs a second person to approve. Everything goes to the audit log.
Neden işe yarıyor?Dört katmanı sayarak söylemek (kimlik, sahiplik, imza, onay) cevabı akılda kalır yapar.
35:00 · Ölçüm ve kapanış
Interviewer
Last one: what would you measure?
Sen
Deploy success rate, how long a deploy takes, how many rollbacks, and the time from merge to production per team. And for the API itself the normal ones: error rate and latency.
Interviewer
Great, thanks. That's all from my side.
Neden işe yarıyor?"Merge'den production'a süre" platform ekibinin gerçek başarı ölçüsü: geliştirici deneyimini önemsediğini gösterir.
