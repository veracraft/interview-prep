Akış: 1–4. aşama

Minimum çözüm 1–2. aşama (polling ile çalışır). 3 (tool'lar) ve 4 (canlı akış) soruda istendiği için ilk çizime dahil. 5. aşama follow-up: Ölçek ve follow-up →

Aşamaların yazılı özeti
  1. 1 · Temel istek. İstemci POST /tasks ile bir task başlatır (ok 1); istek gateway'den geçer (ok 2). Agent Tasks API Idempotency-Key'i kontrol eder, task satırını Postgres'e 'queued' olarak yazar (ok 3) ve 202 + task id döner. İstemci GET /tasks/{id} ile polling yapar. En basit, sağlam hal.
  2. 2 · Asenkron yürütme. Task satırıyla aynı transaction'da bir pending_events satırı yazılır; event publisher onu okur (ok 4) ve Kafka'daki task-queue topic'ine yazar (ok 5). Agent worker mesajı alır (ok 6), task'ı lease ile sahiplenir, LLM'i çağırır (ok 7) ve her adımdan sonra durumu Postgres'e kaydeder (ok 8, checkpoint). API pod'u ölse ya da deploy olsa bile task devam eder; worker ölürse lease biter, başka worker kaldığı yerden devralır.
  3. 3 · Tool çağrıları. Model bir tool isterse worker tool executor'ı çağırır (ok 9); executor Jira, CRM gibi uygulamaları kullanıcının kendi OAuth'u ile çağırır (ok 10). Timeout zorunlu. Yazan tool'larda idempotency key ve gerekirse kullanıcı onayı; timeout sonrası sonuç belirsiz olabilir.
  4. 4 · Canlı akış. Worker her olayı (token, tool başladı, bitti) sıra numarasıyla Redis stream'e yazar (ok 11). Agent Tasks API stream'den okur (ok 12) ve SSE ile gateway üzerinden istemciye akıtır (ok 13–14, kesikli). Bağlantı koparsa istemci Last-Event-ID ile kaldığı yerden devam eder. Çalıştıran ile yayın yapan ayrı olduğu için kopma task'ı öldürmez.

Kullanıcı canlı ilerlemeyi görür mü?

Evet. Soruda zaten isteniyor ("users want to see the answer streaming"). Worker her olayı sıra numarasıyla Redis stream'e yazar (ok 11), API okur (ok 12) ve SSE ile istemciye iletir (ok 13–14).

  • Bağlantı koparsa: istemci Last-Event-ID: 41 ile tekrar bağlanır, 42'den devam eder. Task o sırada çalışmaya devam etmiştir.
  • Çok geç dönerse: stream 24 saat saklanır; sonrasında 410 döner, istemci GET /tasks/{id} ve mesaj geçmişiyle son hali çeker.
  • Slack: bot her harfte değil, ~1 saniyede bir mesajı günceller (Slack'in limitleri).
  • Entegrasyonlar: akış istemeyen müşteri webhook_url verir; task.completed (ve onay gerekiyorsa task.requires_action) webhook olarak gelir.
  • Hedef: ilk olay, model süresi hariç p95 < 500 ms.
Users see progress live: tool started, partial answer, approval request, done. The worker writes numbered events to a Redis stream, the API streams them over SSE, and a client that reconnects sends Last-Event-ID and continues. Integrations that don't want a stream get a webhook.
I'd ship polling first because it's simple and robust, then add streaming once the task lifecycle is solid. Where would you like me to go deeper?
