Tenant token'dan nasıl gelir?

Evet, token'daki bir claim'den. Kullanıcı giriş yaptığında kimlik sağlayıcı (IdP: Okta, Auth0 ya da şirketin kendi auth servisi) ona imzalı bir JWT verir. JWT'nin ortasındaki kısım (payload) claim'lerdir:

{
  "sub": "user_ali",            ← kim
  "org_id": "ten_42",           ← hangi müşteri (tenant)
  "roles": ["admin"],           ← ne yapabilir
  "iss": "https://auth.acme.com",
  "exp": 1794310000             ← ne zamana kadar geçerli
}
  1. Gateway imzayı doğrular. IdP'nin public key'iyle (JWKS) imzaya, iss'e ve exp'e bakar. İmza tutuyorsa claim'lere güvenilir: biri org_id'yi değiştirirse imza bozulur, istek 401 alır.
  2. Doğrulanmış claim'ler servise geçer. Gateway X-Tenant-Id: ten_42 gibi bir header ekler ve istemciden gelen aynı isimli header'ı siler. (Ya da servis token'ı kendisi tekrar doğrular.)
  3. Servis tenant'ı sadece buradan alır. Body'de ya da URL'de bir tenant alanı olsa bile ona bakmaz; her sorgu bu tenant ile sınırlanır.

Diğer çağıranlar: CI'ın OIDC token'ında repo bilgisi var; API repo → takım eşlemesini kendi veritabanında tutar. API key kullanan entegrasyonlarda key veritabanında bir tenant'a bağlıdır. Birden çok müşteriye üye bir kullanıcı organizasyon seçince o organizasyon için yeni bir token alır.

The tenant comes from a claim in the signed token, like org_id. The gateway verifies the signature and expiry, so the client can't change it, and the service never reads the tenant from the body.

Event publisher nerede çalışır?

Kısa cevap: Aynı repoda, ama API'den ayrı bir süreç olarak. pending_events ve event publisher nedir, sözlükte.

cmd/api/main.go
cmd/event-publisher/main.go
cmd/sync-worker/main.go       (Agent Tasks'ta: cmd/agent-worker)
internal/...                  (store, domain, events: ortak kod)
  • Tek Docker imajı, farklı başlatma komutu. Her biri ayrı Kubernetes Deployment.
  • Neden ayrı? API, HTTP trafiğine göre ölçeklenir (HPA). Publisher'a 1–2 replika yeter. Publisher çökerse ya da deploy edilirse API etkilenmez. Kendi metriği olur: pending_events lag, yani gönderilmemiş en eski satırın yaşı.

Publisher'ın döngüsü

BEGIN;
SELECT id, topic, payload FROM pending_events
 WHERE published_at IS NULL
 ORDER BY id LIMIT 100
 FOR UPDATE SKIP LOCKED;          -- iki replika aynı satırı almaz
-- her satırı Kafka topic'ine gönder
UPDATE pending_events SET published_at = now() WHERE id = ANY($ids);
COMMIT;
  • Gönderdikten sonra, işaretlemeden önce çökerse mesaj iki kez gider (at-least-once). Tüketiciler idempotent olduğu için sorun olmaz.
  • Gönderilmiş satırlar periyodik olarak silinir (ör. 7 gün sonra).

It lives in the same repo but runs as its own process: same image, different entrypoint, separate deployment. It polls pending_events with SKIP LOCKED, publishes, and marks rows as sent. It's at-least-once, so consumers are idempotent.

Bedeli–"37. sayfaya atla" yapılamaz. API'lerde buna zaten pek ihtiyaç olmaz.
-- offset
SELECT * FROM documents WHERE tenant_id = $t
 ORDER BY created_at DESC, id DESC LIMIT 50 OFFSET 10000;

-- cursor: (created_at, id) son görülen satırdan gelir
SELECT * FROM documents WHERE tenant_id = $t
   AND (created_at, id) < ($son_tarih, $son_id)
 ORDER BY created_at DESC, id DESC LIMIT 50;
  • id sıralamaya eklenir, çünkü aynı created_at'e sahip iki satır olabilir.
  • İstemciye opak bir base64 string verilir (next_cursor); istemci içeriğine bağımlı olmasın. Sayfa boyutuna üst sınır konur.
  • Kaynağın delta cursor'ı (Drive'ın changes token'ı) başka bir şeydir; ortak yanı "kaldığım yer" demesi.
Offset makes the database read and throw away all skipped rows, and rows shift when new ones are inserted. A cursor says "give me the next 50 after this one", so it uses the index, stays fast, and doesn't skip or repeat items.

Multi-tenancy: WHERE tenant_id yeterli mi?

Hayır. O tek bir katman; bir sorguda unutulursa veri sızar. Katman katman korunur (defense in depth):

KatmanNe yapılır?
Kimlik / gatewaytenant_id sadece doğrulanmış JWT'den gelir; body, header ya da path'ten asla alınmaz. Başka tenant'ın kaynağı istenirse 404 dönülür (403 değil; kaynağın varlığını da sızdırmaz).
BackendTenant request context'te taşınır. Store katmanında tenant parametresi almayan metot olmaz. Redis key'leri, idempotency key'leri ve cache'ler tenant prefix'li olur.
PostgresHer tabloda tenant_id olur ve composite index'in ilk kolonudur. Foreign key'ler tenant'ı da içerir, böylece A'nın dokümanı B'nin kaynağına bağlanamaz. RLS açılır; uygulama rolü tablo sahibi olmaz ve BYPASSRLS yetkisi almaz. Kod WHERE'i unutsa bile DB engeller.
AsyncHer mesaj tenant_id taşır; worker DB'ye dokunmadan önce tenant'ı yeniden ayarlar. Tenant başına rate limit ve adil sıralama olur; bu da performans izolasyonudur (noisy neighbor).
Depolama / cloudGCS yolu tenants/{id}/… olur. OAuth token'ları Secret Manager'da tutulur. Büyük kurumsal müşteriye kendi KMS anahtarı (CMEK) verilir. Bölge seçimi yapılır (AB verisi AB'de kalır).
İzolasyon modeliPooled (ortak DB + RLS) → bridge (büyük tenant'a ayrı schema veya DB) → silo (regüle müşteriye ayrı proje veya cluster).
DevOps / testHer endpoint için otomatik test: "A'nın token'ı + B'nin id'si → 404". RLS testleri owner ile değil, uygulama rolüyle koşulur. Log ve trace'te tenant_id olur. Destek erişimi break-glass ile ve audit log'a yazılarak verilir. Tenant silinince DB, vektörler, GCS ve cache temizlenir.
-- A'nın dokümanı B'nin kaynağına bağlanamaz
FOREIGN KEY (tenant_id, source_id) REFERENCES sources (tenant_id, id)

-- RLS
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id'));

-- her transaction başında (connection pool yüzünden SET değil SET LOCAL)
SET LOCAL app.tenant_id = 'ten_42';
Tenant isolation is defense in depth: the tenant comes only from the verified token, every query is scoped, Postgres row-level security catches mistakes, and we test cross-tenant access on every endpoint.
